# 모아온 복구 검토 운영 활성화 점검표

P1-04-10 및 후속 공급자 모듈의 코드 배포는 기능 공개 승인이 아니다. 아래 항목을 증거와 함께 확인하기 전 새 주소·MFA·복구 운영자를 운영에 연결하지 않는다.

| 조건 | 필요한 증거 | 현재 범위 |
|---|---|---|
| 최근 추가 인증 | 실제 공급자의 MFA challenge/verify 성공, 사용자·현재 허브 세션 연결, 발급 시각·만료·폐기 기록 | P1-04-11-1 공급자 검증과 P1-04-11-2 암호화 저장/세션 증거 코드·로컬 검증 완료. 실제 계정 및 운영 활성화는 미완료 |
| 위조·다른 세션 재사용 | 공급자 서명/현재 상태 확인, 타 사용자·로그아웃·재로그인 후 과거 증거 거부 | 합성 검증 사례 + 실제 공급자 시험 필요 |
| 내부 운영자 지정 | 별도 승인된 최소 운영자 목록, 권한 추가/회수 감사, 일반 OWNER와 구분 | 자동 등록 없음 |
| 요청 제한 | 여러 DB 연결의 동시 경합 시험, 운영량 기준 한도 승인 | DB 고정 후보 한도 시험; 운영 정책 미활성 |
| 로그인 전 공격 제한 | 신뢰된 프록시/IP, WAF·서비스 입구 제한, 직접 접속 우회 거부 | 이번 인증 후 제한만으로 대체하지 않음 |
| DB 최소 권한 | 실제 대상 catalog·정책·권한 확인, 후보 SQL 검토 후 migration, rollback 절차 | 운영 SQL 미적용 |
| 세션 폐기 시점 | 추가 인증/쿼터 대기 중 폐기 차단, 발송 직전 검사, 이미 발송된 작업 처리 정책 승인 | 이미 발송된 작업의 원자적 취소를 보장하지 않음 |
| 네트워크·메일 | TLS/Origin/프록시 실제 설정, Auth·메일 실패·중복·시간 초과, 비밀값 비노출 | 테스트 대역은 실제 성공 증거가 아님 |
| 업무 격리 | 주문·정산·파일·캐시·로그의 사업장별 권한 시험 | P2 완료 전 공개 다사업장 가입 금지 |
| 사용자 검수 | 기존 로그인 회귀, 실제 지정 운영자 최소 요청, 모니터링·중지 스위치·복구 절차 | 운영자·비밀번호 자동 입력하지 않음 |

공급자 `providerSessionId`와 허브 `sessionId`는 같은 값이 아니다. P1-04-11-2에서 암호화 저장·증거 발급/조회/폐기와 로컬 동시성 검증을 완료했다. 실제 로그아웃 연결과 키 관리·운영 권한은 별도 검수한다. P1-04-12는 복구 검토 요청의 저장된 증거 재검사 연결 단계다. SDK+합성 HTTP 검사로 실제 운영 MFA 성공을 대신하지 않는다.

## 후보 정책

- 인증 증거는 현재 사용자와 현재 세션에 묶고, 5분 미만의 최근 MFA 증거만 허용한다. 세션 만료가 더 빠르면 그 시각까지다.
- 60초 동안 운영자별 조회 30회/종결 10회, 서비스 전체 조회 300회/종결 100회. 운영 수요에 맞는지 활성화 전에 확인한다.
- 제한 초과는 대기 안내 대상이며 자동 재시도로 우회하지 않는다. 승인 후 취소/실패한 요청의 카운터는 되돌리지 않는다.
- 증거 발급기에서 성공을 기본값으로 반환하거나 기존 OWNER 역할·이메일 인증만으로 MFA를 대신하면 안 된다.

## 활성화 순서

1. 합성 자료로 코드·SQL·실제 다중 연결 검증.
2. 별도 승인된 실제 인증 환경에서 MFA 증거 발급·저장·폐기 연결 검증.
3. 운영 DB 권한·이전/복구 계획과 요청 정책 검토.
4. 지정 운영자만 제한적으로 공개해 실사용 검수. 기존 업무 로그인은 유지.
5. 문제 발생 시 신규 진입을 닫고, 이미 전달한 작업은 같은 식별자로 이력을 조회해 정리. 비밀번호 재변경이나 이력 강제삭제로 해결하지 않는다.

참고: [Supabase MFA 공식 문서](https://supabase.com/docs/guides/auth/auth-mfa)는 등록·추가 인증·권한 적용을 각각 요구한다. 허브의 기존 자체 세션과 공급자 세션을 같은 것으로 간주하지 않는다.
