# 하린식품 Windows 전용 업무 프로그램 기획·설계안

> 후속 요청 반영: 앱 UI 조정·초대 사업자 사용 범위는 [다사업장 통합 설계](2026-09-07-multi-business-desktop-hub-design.md)가 우선한다. 이 문서의 단일 사용자·외부 제공 제외 범위는 이전 제안이며, 출력·설치·복구 상세는 새 계획에서 재사용한다.

작성: 2026-09-07. 상태: 사용자 검토용 제안. 이번 작업은 문서 작성과 읽기 전용 조사이며 코드·DB·설치·운영 배포를 변경하지 않는다.

## 1. 목적과 범위

사장님이 Windows PC에 설치파일(.exe)로 설치하고, 바탕화면·작업표시줄에서 실행하는 하린식품 전용 업무 프로그램을 만든다. 외부 고객에게 판매·배포하거나 앱스토어에 등록하지 않는다. 휴대폰 앱·모바일 푸시는 제외한다.

전용 프로그램은 기존 온라인 허브의 인증·데이터·업무 기능에 연결한다. PC에서 모든 서버를 돌리는 완전 오프라인 프로그램은 아니다. PC가 꺼져도 서버의 수집 일정은 계속 실행되는 구조를 유지하고 이를 별도로 검증한다. 프린터 출력은 해당 PC와 프린터가 켜져 있어야 한다.

설치파일 공개 배포와 기존 서버 업데이트는 구분한다. 설치파일은 사장님에게 비공개 전달한다. 서버 개선은 기존 허브의 제한된 운영 업데이트로 처리하며, 웹 버전은 장애 시 대체 수단으로 남긴다. 앱으로 바꾼다고 기존 웹 주소를 폐쇄하거나 데이터 접근 권한을 새로 공개하지 않는다.

기존 계획 중 'PWA 우선, 전용 앱은 나중에 재판정'을 'Windows 전용 앱 우선'으로 변경한다. 기존 성능 개선·수집 안정화·정산·GA4·실행 학습·선택적 Hermes 계획은 유지한다.

## 2. 현재 확인된 기준

- 이번 조회에서 로컬 HEAD와 package.json은1488f44 / v1.39.44. 설치형 웹앱 기반과 날짜 처리 최적화가 존재한다. Windows 전용 실행 프로그램은 아직 없다.
- 기존 배포/테스트 실적은 output/2026-09-07-hub-app-release-report.md에 기록되어 있다. 이 계획 작성 중 운영 속도·전체 테스트·수집을 다시 실행하지 않았다.
- 기존 서버는 Next.js16.3, Node24 계열이다. app/proxy·서버 API·서버 계산을 사용하므로 전체를 정적 파일로 내보내는 변경은 하지 않는다.
- lib/dashboard-auth.js의 현재 세션은12시간, HttpOnly/Secure/SameSite=Lax 쿠키이며 proxy.js는 변경 요청의 동일 출처를 검증한다. 앱에서도 유지한다.
- app/api/shipping/print/route.js에는 A4 작업 문서와100×150mm 라벨이 있다. 현재 라벨 조회는 요청당20건, 작업 문서는100건으로 제한한다. 앱은 제한을 숨기거나 선택 초과분을 누락하지 않는다.
- 이번 OS 조회는 Windows11 Pro64비트. CPU 아키텍처와 실제 출고 PC는 실행 전 별도 확인한다.
- 사장님은 라벨 규격을 정확히 모른다고 답했다. 이 PC의 Get-Printer에는 가상 프린터만 보였다. 실제 라벨 프린터 미등록·다른 PC 사용·연결 상태 중 원인을 단정하지 않는다.100×150mm는 기존 코드 규격이지 실물 규격 확정값이 아니다.

## 3. 제작 방식 비교와 권고

| 방식 | 장점 | 부담·제약 | 이번 판단 |
|---|---|---|---|
| Electron 기반 설치 프로그램 | 기존 JS/웹 화면 재사용, 인쇄·다운로드·창 관리 API, Chromium 환경 일관성 | 실행 엔진 포함에 따른 크기·메모리 비용, 보안 업데이트 필요 | 우선 후보. 기술 검증 후 확정 |
| Tauri 기반 설치 프로그램 | OS 웹뷰 활용, Rust 기반 최소 네이티브 경계 구성 가능 | WebView2·드라이버·인쇄 통합 실증 필요, 현재 Next 서버를 정적 export로 바꿀 수 없음 | Electron의 자원·출력 검증이 부적합할 때 비교 후보 |
| C#/.NET 중심 전면 재구현 | Windows 기능을 직접 설계할 수 있음 | 화면·인증·기능 중복 구현, 회귀·유지보수 범위 증가 | 현재 제외 |

Electron 추천은 인쇄 요구와 현재 코드 구조를 종합한 설계 판단이며 실측 결론이 아니다. Electron과 Tauri 모두 원격 허브를 표시하는 구성이 가능하지만, 기존 Next 서버 코드를 PC 정적 화면으로 그대로 옮길 수 있다는 뜻은 아니다. Tauri의 공식 Next 통합 가이드는 정적 export 전제다. [Tauri Next 가이드](https://v2.tauri.app/start/frontend/nextjs/)

Electron은 main과 renderer를 분리하고 데스크톱 기능을 제공한다. [프로세스 구조](https://www.electronjs.org/docs/latest/tutorial/process-model) 인쇄 프린터·용지·사용자 확인 옵션도 제공하지만 장치별 실제 출력은 별도 시험이 필요하다. [인쇄 API](https://www.electronjs.org/docs/latest/api/web-contents#contentsprintoptions-callback)

## 4. 목표 구조

```text
Windows 설치 프로그램
 ├─ 로컬 프로그램 영역: 창/앱 정보/프린터 설정/저장 대화상자/오류 안내
 └─ 격리된 허브 화면: 기존 HTTPS 허브, 기존 로그인·메뉴·업무
        ↓ 기존 서버의 인증·권한·중복 실행 방지
   Next.js 허브 서버
        ├─ 기존 데이터 저장소: 주문·정산·일정·기록의 기준 원장
        └─ 기존 수집 작업자: Cafe24 / 네이버 / 쿠팡 / 우체국
```

PC가 플랫폼 API를 새로 직접 호출하지 않는다. 쿠팡 고정 IP 수집 경로도 유지한다. 앱은 DB 관리자 키, 플랫폼 API 비밀키, 사용자 비밀번호를 설치파일에 포함하지 않는다. 관련 키가 없는 개발용 PC에서도 패키징할 수 있어야 한다.

앱 버전과 서버 버전을 별도로 관리한다. 초기 앱 예:0.1.0-beta.1, 서버 기준:v1.39.44. 서버가 지원하는 앱 기능 버전과 맞지 않으면 네이티브 작업을 제한하고 이유를 표시하며, 보안상 안전한 경우 웹 대체 경로를 제공한다.

## 5. 사용자 경험과 기본 정책

### 설치·실행

- 대상 파일 형식은 `HarinHub-Setup-<앱버전>-x64.exe`로 제안한다. 실제 CPU 확인 후 아키텍처 확정.
- 일반 사용자 계정 설치를 기본으로 하며, 드라이버를 설치하거나 관리자 권한을 임의로 요구하지 않는다.
- 바탕화면/시작 메뉴 등록, 제거 기능, 현재 버전 확인을 제공한다.
- 중복 실행 시 새 프로세스로 업무를 중복 수행하지 않고 기존 창을 앞으로 가져온다. 별도 인쇄 창은 허용된 작업 창으로 취급한다.
- 창 크기·최대화·모니터 위치를 기억한다. 모니터가 사라졌으면 보이는 화면 안으로 복귀한다.
- 자동 시작과 트레이 상주는 기본 OFF. 닫기는 종료가 기본이다. 사용자가 옵션을 켠 경우에만 트레이 동작을 바꾸며, 실제 종료 메뉴를 제공한다.

### 로그인·화면

- 앱의 독립된 브라우저 프로필에서 기존 로그인 화면을 사용한다. Chrome 로그인 쿠키를 복사하거나 앱에서 암호를 대신 입력하지 않는다.
- 서버 세션 유효 기간 안의 재실행 복귀와 만료 후 로그인 복귀를 검증한다. 영구 자동 로그인으로 바꾸지 않는다.
- 입력 중 로그아웃/만료가 발생하면 변경 요청을 자동 재전송하지 않는다. 개인정보 입력값을 임의로 디스크에 저장하지 않는다.
- 기존 메뉴, 공통 글자 크기, 다크/라이트, 패널 배치를 유지한다. 별도의 앱 메뉴는 '창/인쇄/프로그램 설정/버전·진단' 정도로 제한한다.
- PC 단축키는 앱에 포커스가 있을 때만 적용한다. 새로고침·종료는 진행 중 작업과 입력 유실을 확인한다. 전역 단축키로 다른 프로그램을 가로채지 않는다.

### 외부 로그인·새 창·파일

- 허브 업무는 고정된 운영 HTTPS origin에서만 실행한다. URL 문자열 포함 여부 대신 URL 파서로 protocol/hostname/port/origin을 검증한다.
- 공급자 관리자·OAuth는 기본 브라우저에서 진행하도록 설계한다. 브라우저 쪽 허브 로그인이 필요할 수 있음을 안내하고, 앱 복귀 후 서버의 연결 상태를 다시 읽는다. 쿠키·인증코드를 앱으로 복사하지 않는다. 실행 초기에 실제 OAuth 상태 쿠키 경로와 함께 실증한다.
- 허용된 허브 인쇄 경로만 격리된 인쇄 창에 연다. 나머지 새 창, 리디렉션, iframe, 외부 링크는 목적별 허용 정책을 통과해야 한다.
- 파일 저장은 사용자가 고른 폴더·파일명으로 수행한다. 덮어쓰기 확인, 취소, 디스크 부족, 한글·긴 경로를 처리한다. 자동 파일 실행과 임의 경로 쓰기는 금지한다.
- blob 다운로드는 허브의 검증된 발행 창과 파일 유형을 확인한다. API HTML이 로그인 화면으로 바뀐 경우 이를 PDF/엑셀로 저장하지 않는다.

## 6. 출력 설계: 송장 발급과 인쇄를 분리

1. 송장 번호 발급은 기존 서버·우체국 처리 경로를 사용한다.
2. 이미 발급된 번호의 라벨 출력은 별도 PC 작업이다. 인쇄 실패가 송장 재발급을 유발하면 안 된다.
3. 초기 버전은 인쇄 미리보기/확인 대화상자를 사용한다. 실제 프린터·라벨 검증을 통과한 뒤 명시적 옵션으로 직접 인쇄를 추가한다.
4. 라벨 프린터와 A4 프린터를 구분해 저장한다. 프린터가 사라지면 다른 기본 프린터로 조용히 출력하지 않고 선택을 요청한다.
5. 설정 조회→테스트 표시가 있는 가짜 주문 라벨→실제 크기 측정→잘림·바코드 확인 순서로 검증한다. 테스트 문서를 실배송에 쓰지 않는다.
6.20/21건,100/101건에서 페이지 분할 또는 사전 차단·안내로 누락을 막는다. 선택 순서·완료 목록·실패 목록을 보존한다. 기존 제한을 넘기는 서버 변경은 별도 회귀 테스트가 필요하다.
7. 상태를 '인쇄 준비/사용자 취소/프린터로 전송/결과 확인 필요/사용자 출력 확인'으로 구분한다. OS 호출 성공은 종이가 실제 출력되었다는 증거가 아니다.
8. 오류·앱 종료 후 불명확한 인쇄를 자동 재시도하지 않는다. 사용자 확인 후 재인쇄하고 기존 송장 번호를 재사용한다.
9. 출력물은 고객 개인정보를 포함할 수 있다. 자동 영구 저장을 하지 않고 작업 후 메모리·앱 소유 임시 파일을 정리한다. 사용자가 저장한 PDF와 OS 인쇄 스풀은 별도 보관 범위임을 설명한다.

## 7. 보안·저장·장애 복구

원격 허브 화면은 nodeIntegration=false, contextIsolation=true, sandbox=true를 기본으로 한다. webSecurity/CSP/TLS 검증을 끄지 않는다. 화면에 임의 명령·파일·네트워크 프록시 API를 노출하지 않는다. 네이티브 기능 요청은 발행 창·프레임·origin·스키마·업무 권한·중복 요청을 검사한다. [Electron 보안 권고](https://www.electronjs.org/docs/latest/tutorial/security)

앱의 로컬 설정에는 창 위치·프린터명·사용자 옵션만 넣는다. 표준 브라우저 세션 저장소의 인증 쿠키는 별도이며, 이를 앱 설정 JSON이나 진단 기록으로 내보내지 않는다. 주문/고객 원장과 관리자 키는 로컬에 복제하지 않는다. 앱 프로필 전체가 무조건 암호화된다고 표현하지 않는다. 제거 시 해당 앱의 로그인·로컬 설정 삭제 여부를 안내하고 다른 브라우저 프로필을 건드리지 않는다.

기존 PWA worker는 원격 origin의 제한된 공개 안내 캐시로 남길 수 있지만, 네이티브 업데이트·인쇄·파일 권한을 맡기지 않는다. 앱은 자체 로컬 연결 오류 화면도 갖춘다. worker 업데이트와 앱 업데이트를 독립적으로 검증하고 다른 브라우저/PWA 설치를 임의로 제거하지 않는다.

연결 실패, 서버401/403/500, 자료 미수집, 렌더러 충돌, 프린터 실패를 서로 다른 상태로 표시한다. 재연결 때는 읽기 상태부터 재조회하며 송장·환불·입찰·이벤트 저장을 자동 재실행하지 않는다. 다른 창/기기와의 중복 실행은 기존 서버의 멱등성·잠금으로 막고, 앱 중복 실행 방지만으로 충분하다고 보지 않는다.

진단 기록은 앱/서버 버전, 작업 종류, 요청 추적 ID, 시간, 오류 분류만 남긴다. 주소·전화·문의 원문·쿠키·쿼리 인증정보를 삭제하며, 서버로 보내기 전 사용자가 내용을 확인한다. 클라이언트 버그로 로그가 폭증하지 않도록 크기·보관기간을 제한한다.

## 8. 비공개 전달·업데이트·복구

- 초기에는 검증된 새 설치파일을 사장님에게 직접 전달하고 수동 설치한다. 공개 GitHub Releases·앱스토어·공개 자동 업데이트 채널은 사용하지 않는다.
- `publish: never`에 해당하는 패키징 정책, 명시적 포함 파일 목록, 비밀파일 스캔을 적용한다. `.env*`, 원장·PDF·로그·원본 자료·전체 저장소를 exe에 넣지 않는다.
- 설치파일, SHA-256, 버전표, 변경 내역, 테스트 결과, 이전 설치파일을 함께 보관한다. 해시만으로 발행자 신뢰가 증명되는 것은 아니므로 신뢰된 전달 경로와 서명 정책을 따로 둔다.
- Windows 코드 서명 여부는 기술 검증 단계에서 비용·신원 확인을 설명한 뒤 결정한다. 초기 비서명 시험본은 비서명이라고 표시한다. 서명해도 경고가 무조건 사라지는 것은 아니며 Defender/SmartScreen을 끄도록 안내하지 않는다. [Microsoft SmartScreen](https://learn.microsoft.com/en-us/windows/security/operating-system-security/virus-and-threat-protection/microsoft-defender-smartscreen/)
- 서버 화면 업데이트와 exe 업데이트는 별개다. 서버 변경은 구 앱과의 호환성을 검증하고, exe 변경은 작업 종료 후 설치한다. 진행 중 출고·인쇄를 강제 종료하지 않는다.
- 자동 업데이트는 초기 필수 기능에서 제외한다. 추후 필요하면 비공개 인증 저장소·서명 검증·만료·단계적 적용을 별도 설계한다. [Electron 업데이트 안내](https://www.electronjs.org/docs/latest/tutorial/updates)
- 되돌리기는 이전 설치파일+호환 가능한 설정 버전으로 한다. 앱 롤백이 서버 DB·실제 송장·환불을 되돌리는 것은 아니다. 서버 변경도 별도 이전 버전·데이터 이력으로 복구한다.

## 9. 기존 계획의 통합·변경표

| 기존 항목 | 새 계획 |
|---|---|
| R0 안전·성능 기준선 | W0/W6/W7에서 앱 환경 기준 재검증.24시간 예정 수집 회차 확인 유지 |
| R1 지연 감소 | W6. v1.39.44 날짜 최적화는 재개발하지 않고 서버 조회 대기부터 측정 |
| R2 PWA·모바일 | 모바일·푸시는 제외. PWA 강제 제거 없이 Windows 설치파일 W1~W5로 대체 |
| R3 정산·GA4 | B1. 실제 원천·권한·태그 준비 조건 유지. 데스크톱 앱 완성의 선행 조건은 아님 |
| R4 사장님 실행 학습 | B2. 기존 인사이트·실행검증·실험을 연결 |
| R5 Hermes | B3. 선택적 읽기 전용 격리 시험, 별도 구매·모델 비용 결정 |
| R6 소재·예산·사은품 | B4. 실제 근거와 실행 안전 확인 후 연결 |
| R7 전용 앱 재판정 | W0~W7의 주 개발 범위로 승격. 전면 화면 재개발은 제외 |

### B1: 정산·측정의 실제 운영 완료

Cafe24 공식몰 Naver Pay 주문과 네이버 스마트스토어 주문을 분리한다. 쿠팡 판매자배송과 로켓그로스도 원장·정산 기간·수수료·물류비·광고비·지급을 분리한다. 총매출, 예상 지급, 실제 지급, 비용 차감 후 이익을 서로 다른 항목으로 유지한다. 광고비 충전과 실제 광고 소진 비용을 중복 비용으로 합산하지 않는다. API 미지원 자료는 파일/수동 근거와 갱신 시점을 표시한다.

GA4는 방문·구매·환불 관측이며 주문·정산의 최종 원장이 아니다. 기존 코드와 UTM 기능을 재사용하고 속성·서비스 계정·호스트·시간대·구매/환불 이벤트를 확인한다. 테스트 구매/환불은 별도 승인 시나리오이며 개인정보·비밀키를 채팅이나 앱에 저장하지 않는다.

### B2: 사장님 실행 학습

네이버 한 상품·한 채널에서 '근거→가설→행동 하나→실행 이력→7/14일 회고'를 연결한다. 승인 자료 버전·UTM·가격·재고·이벤트·시즌 변화를 함께 남긴다. 자동 주간 보고는 원천·기간·버전으로 중복을 막고, 같은 데이터의 재작성은 이력으로 관리한다. 표본이 부족하거나 인과 효과를 분리할 수 없으면 판단 보류를 표시한다.

### B3: Hermes 선택 시험

아침 운영 요약과 네이버 주간 행동 제안 두 작업만 집계 자료를 읽도록 한다. 기존 수집 작업자와 호스트/권한을 격리하고 고객 주소·전화·상담 원문·DB 관리자 키를 주지 않는다. 일일 비용·시간·재시도 상한과 중지 장치를 둔다.14일 동안 근거 정확성·중복 알림·준비 시간·비용을 기존 방식과 비교한다. 기본 모델이 우리 자료로 자동 재학습된다고 설명하지 않는다. 효용이 없으면 제거해도 주문·정산은 계속 동작해야 한다.

### B4: 제작·예산·포장 지원

승인된 상품/표현 자료로 소재·랜딩 초안, 검수, 버전, UTM과 결과를 연결한다. 원가·재고·광고 귀속이 준비된 경우에만 예산 시나리오를 제공한다. 자동 광고비 증액·자동 게시·가격 변경은 기본 범위 밖이다. 사은품 대상 판정은 기존 캘린더 규칙을 그대로 사용하고 포장 체크 이력을 연결해 중복 동봉을 방지한다.

## 10. 완료의 정의

설치파일이 만들어졌다는 것과 실무 사용 준비가 끝났다는 것은 다르다. 지원 대상 PC에서 설치/로그인/전 페이지/저장·업로드/출력/장애 복구/업데이트/제거가 통과하고, 앱·브라우저의 동일 원천 금액과 주문 ID가 일치해야 업무용 완료로 판정한다. 실프린터가 없으면 조회용 베타만 가능하며 '출고용 검증 완료'라고 하지 않는다.

구체적인 작업·테스트·단계별 통과 기준은 [통합 개발계획](../plans/2026-09-07-windows-private-hub-roadmap.md)에 둔다. 본 문서는 검토용이며 기술 검증 전 프레임워크·프린터·비용을 확정하지 않는다.
