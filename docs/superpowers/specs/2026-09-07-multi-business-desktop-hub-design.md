# 다사업장 Windows 허브 통합 기획·아키텍처 제안

작성일: 2026-09-07. 상태: 사용자 승인 후 모아온(MOAON)으로 단계별 구현 착수. 본 문서는 목표 설계이며 실제 다사업장/DB 전환/설치파일의 완료를 뜻하지 않는다.

## 1. 목표와 이전 계획 변경

동일한 Windows 설치 프로그램에서 사용자가 본인 계정으로 로그인하고, 권한이 있는 사업장의 쇼핑몰·광고·배송 계정을 직접 연결해 업무를 수행한다. 하린식품은 기존 자료를 보존한 첫 사업장, 듀모르는 새 자료로 시작하는 두 번째 사업장의 예다. 듀모르의 실제 소유권·계정·연결 가능 플랫폼은 아직 검증하지 않았다.

이번 제안은 `2026-09-07-windows-private-hub-design.md`와 대응 roadmap을 확장한다. 변경 충돌 시 이 문서와 새 통합 roadmap을 우선한다.

| 항목 | 이전 제안 | 새 제안 |
|---|---|---|
| 사용 범위 | 사장님 전용 | 초대받은 다른 사업자도 독립 사용 |
| 화면 | 현 UI 유지 | 기존 디자인을 바탕으로 앱용 배치·사업장 표시 조정 |
| 계정 | 현 로그인 유지 | 인증 기반 유지 + 사업장별 멤버십·역할·가입/복구 |
| 연결 | 기존 서버 설정 재사용 | 사업장·플랫폼 계정별 인증정보와 수집 상태 관리 |
| 전달 | 사장님에게 비공개 EXE | 초대 사용자에게 비공개 EXE, 공개 판매·자동 결제 제외 |
| 제작 | Windows Electron 우선 실증 | 유지. 계정/사업장 경계를 먼저 확정해 재작업 방지 |
| 검증 | 단일 사업장 업무 | 기존 회귀 + 두 사업장 격리·동시 작업·이전 검증 |

모바일 앱·앱스토어·공개 회원가입·구독 결제·사업장 간 통합 매출 화면·커스텀 도메인·전체 UI 재개발은 1차 범위에서 제외한다. 공개 판매를 원하면 별도 약관/지원/과금/유통 설계를 거친다. 초대제라도 다른 사업자의 개인정보를 취급하는 운영 책임은 사라지지 않는다.

## 2. 현재 코드에서 확인한 근거

이번 읽기 조사 기준 HEAD `1488f44`, package `1.39.44`. 운영 DB 스키마/실계정 권한/전체 API 테스트 결과를 새로 검증한 것은 아니다.

- `lib/dashboard-auth.js`: Supabase Auth 비밀번호 인증, 자체 서명 세션과 `dashboard_sessions`, 12시간 만료, OWNER/OPERATOR/VIEWER 정의가 이미 있다. 로그인 자체가 없는 서비스가 아니다.
- `proxy.js`: 현재 보호 경로는 OWNER 중심이며, 다른 역할의 전 페이지 접근을 허용하는 설계가 아니다. 인증된 사용자와 사업장 소속 권한을 분리해야 한다.
- `lib/cafe24/supabase.js`: 공통 service-role 클라이언트 사용. RLS 설정만 추가하면 서버 조회도 자동 격리된다고 생각하면 안 된다.
- `lib/coupang/config.js`, `lib/naver/client.js`, `lib/cafe24/config.js`: 플랫폼 계정이 환경변수 중심이다. 전역 환경변수를 요청마다 교체하는 방식은 금지한다.
- `lib/cafe24/token-store.js`: 몰 ID 기반 토큰 저장, 로컬 공통 임시 파일 fallback 존재. 다사업장 런타임에서는 공통 토큰 파일 fallback을 사용하지 않는다.
- `lib/coupang/request-queue.js`: request type/멱등 키 기준 대기열 조회가 있어 사업장/연결 단위 격리가 필요하다.
- `lib/owner-workspace.js`: 저장 보기·업무 조회에 사업장 조건이 없는 경로가 있다.
- `app/_phase28/phase28-shell.js`: 하린식품 브랜드 문구와 공통 알림 조회가 있어 사업장 컨텍스트 적용 대상이다.
- 기존 쿠팡 생성 migration에 단독 외부 ID unique가 보인다. 현재 전체 스키마를 조사한 뒤 복합 키·upsert·외래키를 함께 이전해야 한다. 오래된 migration만 보고 현재 DB 구조를 단정하지 않는다.

## 3. 제공 방식 비교와 추천

| 방식 | 장점 | 비용/위험 | 판단 |
|---|---|---|---|
| 사업자별 코드·서버 복제 | 초기 물리 분리 쉬움 | 수정·배포·인증설정 중복, 기능 차이 발생 | 기본안 아님 |
| 한 서비스 + 사업장별 데이터 격리 | 동일 EXE·서버를 관리, 초대와 전환 용이 | 모든 데이터 경로의 격리 검증 필수 | 1차 추천 |
| 공통 관리 + 사업장별 DB 프로젝트 | 더 강한 물리적 격리 선택 가능 | 프로젝트 비용·마이그레이션·백업·운영 복잡성 | 격리 요구가 높은 고객용 후속 옵션 |

추천은 공통 서버와 DB에서 논리 격리를 강제하는 구조다. 향후 사업장별 저장소로 이전할 수 있게 데이터 접근 계층을 분리하지만, 1차부터 두 저장 방식을 모두 구현하지 않는다. 격리 시험을 통과하지 못하면 두 번째 실사업장을 열지 않는다.

## 4. 사용자·사업장·브랜드·플랫폼의 관계

```text
Windows 프로그램 / 기존 웹(비상 접속)
  └─ 개인 사용자 계정
      └─ 사업장 멤버십과 역할
          ├─ 하린식품 사업장 → 하린식품의 몰·광고·우체국 연결
          └─ 듀모르 사업장   → 듀모르의 몰·광고·배송 연결
                 └─ 각 연결의 주문·제품·정산·수집 작업·근거
```

- `tenant`는 독립 데이터 소유·운영 권한 경계인 사업장이다. 사업자등록번호를 내부 PK로 사용하지 않는다.
- 사업장 이름/브랜드와 법적 사업자가 반드시 1:1은 아니다. 1차에서는 서로 섞지 않을 운영 단위를 별도 사업장으로 만들며, 법인/브랜드 계층 확장은 별도 범위다.
- 한 사용자가 두 사업장의 멤버일 수 있지만 권한도 각각 다르다. 듀모르만 초대받은 사용자는 하린식품의 이름·개수·알림도 보지 못한다.
- 같은 사업장에 복수 몰/광고 계정을 담을 수 있도록 데이터 모델을 만든다. UI도 연결 추가 목록을 제공하되, 채널별 다중 계정 실증이 완료된 조합만 허용한다.
- 회원가입만으로 다른 사업장의 소유자가 되지 않는다. 사업자번호 입력이나 몰 이름 유사성도 소유 증거가 아니다.

## 5. 가입·로그인·초대·역할

### 시작 흐름

초대 링크 → 이메일 확인 및 본인 비밀번호 설정 → 기존 사업장 참여 또는 허용된 새 사업장 생성 → 사업장 정보 → 플랫폼 연결 → 읽기 검증 및 첫 수집 → 기준 설정 → 홈.

초대는 사업장·이메일·역할에 결합한 만료/일회용 토큰을 사용한다. 동일 링크 재사용/다른 이메일 수락/취소된 초대를 거부한다. 생성 실패를 재시도해도 동일 사업장·멤버십이 중복 생성되지 않아야 한다. 신규 사업장 생성 권한은 초대 유형으로 구분한다.

기존 Supabase Auth를 인증 공급자로 유지하고 서버 세션 계약을 확장한다. 자체 비밀번호 저장 시스템을 새로 만들지 않는다. 초기에는 기존 인증 동작을 호환 계층으로 유지하며, 전체 SSR 세션 교체는 필요성이 입증되지 않으면 하지 않는다. 비밀번호 재설정 후 기존 허브 세션도 폐기한다. 신규 OWNER 계정의 MFA와 계정 복구는 다사업장 출시 검증 항목으로 포함하며, 기존 사용자를 사전 검증 없이 잠그지 않는다.

| 역할 | 기본 권한 |
|---|---|
| OWNER | 해당 사업장 구성원·연결·운영 설정, 업무 수행, 데이터 내보내기 |
| OPERATOR | 해당 사업장 주문·배송·CS 등 허용된 실무. API 키/구성원/사업장 삭제 불가 |
| VIEWER | 허용된 조회, 고객 연락처/주소 기본 마스킹. 일괄 개인정보 내보내기·인쇄 불가 |
| 서비스 운영 관리자 | 초대 발급·장애 메타데이터. 사업장 OWNER와 별개이며 고객 원문 상시 조회 권한 아님 |

역할은 메뉴 노출이 아니라 API 실행 권한으로 검사한다. OPERATOR의 정산 전체 조회/개인정보 export 등은 권한표에서 명시하고 기본 거부한다. 마지막 OWNER 삭제/탈퇴를 금지하고 소유권 이전은 새 OWNER 수락·재인증·이력을 남긴다. 탈퇴한 사용자는 기존 세션/JWT의 오래된 역할로 업무를 계속할 수 없어야 한다.

서비스 관리자 지원 조회는 사업장 동의·기간 제한·사유·감사 기록을 요구한다. DB 운영자의 기술적 접근 가능성까지 없다고 주장하지 않는다. 이용 안내에 관리자·데이터 처리 주체를 명확히 표시한다.

## 6. 요청·DB 격리 계약

브라우저/EXE는 사업장 ID를 선택값으로 보낼 수 있지만 서버가 세션·활성 멤버십·권한을 확인한 뒤에만 이를 채택한다. 클라이언트 헤더, URL, localStorage, user_metadata의 역할을 신뢰하지 않는다.

권장 1차 접근 모델은 서버 API 경유다. 기존 자체 세션이 곧 Supabase JWT인 것처럼 `auth.uid()` 정책만 붙이지 않는다. 신규 tenant 저장소는 서버가 검증한 컨텍스트를 트랜잭션 로컬로 설정하고, 테이블 소유자도 BYPASSRLS도 아닌 제한된 DB 역할로 접근하는 방식을 실증한다. 풀 재사용 시 이전 tenant 값이 남지 않게 BEGIN/SET LOCAL/COMMIT·ROLLBACK 경계를 시험한다. 멤버십 검증용 제어 저장소와 업무 저장소 권한을 구분한다.

이 방식은 서버 검증을 신뢰 경계로 갖는다. 임의 tenant 설정 SQL/범용 RPC/테이블명·SQL 전달 API를 외부에 노출하지 않는다. 사용자 직접 Data API/Realtime 접근은 초기에는 열지 않는다. 직접 구독이 필요하면 공급자 JWT·RLS·채널 권한까지 별도 검증한 후 제공한다. 기본 갱신은 인증된 사업장별 API 조회를 사용한다.

전체 업무 테이블은 tenant_id NOT NULL, 연결 자료는 connection_id도 포함한다. 외래키는 (tenant_id, 참조 ID) 소유 일치를 보장한다. unique/upsert/멱등 키는 tenant_id + connection_id + 원천 타입 + 외부 키를 적절히 조합한다. 내부 UUID는 유지할 수 있지만 단독 ID 조회에도 권한 검증이 필요하다.

RLS·테이블 권한·뷰·함수·스토리지 정책을 같이 검증한다. 현재 service-role이 지나가는 기존 경로는 자동 보호되지 않는다. 고객용 신규 경로에서 service-role 범용 조회를 제거하거나 좁은 내부 인터페이스로 격리한다. 기존 단일 사업장 경로가 남아 있으면 하린식품 호환 전용으로 서버가 고정 매핑하고 다른 사업자의 도달을 차단한다.

## 7. 데이터 모델과 격리 범위

제안 엔터티(현재 존재한다고 주장하지 않음):

| 엔터티 | 핵심 정보/제약 |
|---|---|
| tenants | UUID, 표시명, 상태, 시간대, 설정 버전 |
| tenant_memberships | tenant_id,user_id,role,status,version; 쌍 unique |
| tenant_invitations | tenant_id 또는 생성권한, 이메일, 역할, 토큰 hash, 만료, 수락/폐기 |
| platform_connections | tenant_id,provider,external_account_id,shop_no,권한·연결 상태,credential_version |
| credential_secrets (비공개) | connection 소유, 암호문, key version, 상태; 원문 반환 금지 |
| tenant_settings | 사업장별 반송지/배송계약/원가·세율·이벤트·AI 규칙의 버전 |
| sync_runs / job scopes | tenant,connection,job_type,cursor,watermark,권한/연결 버전,시도·결과 |
| audit_events | actor,tenant,action,target,outcome,request_id; 비밀정보 제외 |
| device preferences | user+tenant+device+document type별 프린터/레이아웃; 플랫폼 키 없음 |

격리 대상은 주문·상품·CS·정산만이 아니다. 원본 응답, 첨부파일, 검색/자동완성, 이미지 사본, export/PDF, 예약작업, 실패 대기열, 락, 캐시, 알림·사이드바 배지, 매출 목표, 저장 보기, 이벤트, AI 대화·문서·검색 인덱스·평가 결과까지 포함한다. 공유 허용 자료는 비개인 공개 레퍼런스/디자인 토큰뿐이며 공유 자격을 명시한다.

AI 문서의 tenant 태그만 붙이는 것으로 끝내지 않는다. 검색 호출 전에 scope를 제한하고 결과·캐시·첨부·후속 대화까지 동일 경계를 검증한다. 하린식품 자료를 듀모르의 기본 지식으로 복사하거나 사업장 간 모델 학습에 자동 사용하지 않는다.

## 8. 플랫폼 연결센터

API 주소를 사용자가 임의 입력하는 범용 프록시를 만들지 않는다. 지원 플랫폼 카드를 선택하면 공식 인증 방식과 필요한 항목만 노출한다. 도메인/몰 ID는 정규화·허용 목록으로 검사해 SSRF를 차단한다.

| 연결 | 제안 UX | 출시 전에 증명할 조건 |
|---|---|---|
| Cafe24 | 몰 확인 → 공식 OAuth 동의 → 몰/상점번호 확인 | 앱 유형·외부 몰 설치 허용·요청 scope·콜백 등록 |
| 네이버 커머스 | 허용된 내스토어/솔루션·대행 인증 유형에 맞춘 안내 | 외부 사업자 서비스에 맞는 공식 유형/승인; 내스토어 키로 타 판매자 접근 불가 |
| 네이버 검색광고 | 광고계정 식별·키 등 공식 요구 필드 | 광고계정 권한, 커머스 연결과 별도 시험 |
| 쿠팡 | 판매자 ID와 공식 발급 키, 등록 IP 안내 | 타사 연동 요건, 고정 IP, 판매자 일치·기능별 지원 |
| 우체국 | 사업장 계약/인증/발송·반송 정보 입력 | 해당 사업장 계약과 발급 권한, 실제 프린터 검증 |
| GA4 | 속성 ID와 적법한 읽기 권한 설정 | 실제 속성 접근·공식몰 식별; 주문 원장과 별도 |

플랫폼 앱 자체의 client secret과 판매자의 액세스/갱신 토큰은 별도 개념이다. 모든 이용자에게 개발자용 비밀키 입력을 요구하지 않는다. 플랫폼이 허용한 BYOK 방식만 제공하며 개인용 키 보관이 제3자 서비스 이용 요건을 면제한다고 가정하지 않는다. 필요한 심사/계약은 출시 외부 조건으로 관리한다.

연결 과정: 작성 중 → 인증 확인 → 계정 확인 → 읽기 권한 검증 → 첫 수집 → 읽기 사용 가능. 쓰기 권한은 별도 확인 후 소유자에게 켠다. 상태 축을 auth_status, sync_status, capabilities로 분리해 '인증 성공=모든 정산·광고 수집 성공'으로 보이지 않게 한다.

오류는 잘못된 키, 권한 부족, IP 불일치, 승인 대기, 호출 제한, 공급자 장애, 일부 데이터 누락을 구분한다. 마지막 성공 시각/수집 범위/다음 시도/조치 안내를 제공한다. 아직 연결 안 된 사업장에 샘플 실매출이나 하린식품 수치를 보여주지 않는다.

### 인증정보 수명주기

- 키/토큰은 서버에서 암호화하고 암호화 키는 DB 암호문과 분리된 비밀관리 수단에 보관한다. 키 버전과 교체·복구 절차를 포함한다. 로그/응답/앱 설정/설치파일에는 원문을 넣지 않는다.
- 입력 후 마스킹만 보여주고 비밀값 재조회 API를 만들지 않는다. 교체 전 새 계정 일치를 검증한다.
- OAuth state는 tenant,actor,session,connection intent,provider,만료·일회용 nonce에 결합한다. callback에서 현재 사업장 선택값으로 귀속시키지 않는다.
- 앱→브라우저 인증 이동은 짧은 일회용 서버 intent를 사용하고 비밀번호/토큰을 URL에 싣지 않는다. 브라우저 로그인 계정이 다르거나 세션이 바뀌면 거부한다. state 위조·재사용·두 사업장 동시 연결을 시험한다.
- refresh는 연결별 분산 락/CAS로 직렬화한다. 해제 중 완료된 refresh가 폐기된 연결을 되살리지 못하도록 버전을 검사한다.
- 동일 실제 판매자 계정을 두 tenant에 붙이는 것은 기본 차단하고 계정 정보 노출 없이 안내한다. 소유권 이전은 구 연결 중지·예약작업 정리·원장 소유 검토를 거치는 별도 절차다.
- 연결 해제는 신규 예약 중지·대기 작업 취소·토큰 폐기·가능한 원격 revoke·진행 작업 결과 확인 순서다. 완료한 주문/송장 원장을 자동 삭제하지 않는다.

## 9. 자동 수집·작업 실행

사업장/연결별 스케줄·커서·최근 성공·실패·재시도·쿼터를 저장한다. 전역 FULL 요청 하나가 모든 사업자의 상태를 대표하지 않는다. 대량 사업장의 backfill이 다른 사업장의 신규 주문을 막지 않도록 공정 배분과 연결별 동시성 제한을 둔다. 공급자 전역 제한도 함께 지킨다.

각 작업은 tenant,connection,connection_version,업무 타입,기간,멱등 키를 고정한다. 실행 시 연결 상태를 다시 확인하고, 사용자 실행 작업은 현재 멤버십/행위 권한도 재검증한다. 정기 수집은 승인된 사업장 자동화 서비스 주체로 수행한다. 작업 payload에 비밀키를 넣지 않는다.

외부 API가 멱등 키를 지원하지 않으면 성공 여부 불명의 쓰기를 자동 재시도하지 않는다. 원천 조회/기록 대조 후 사람 확인으로 보낸다. '정확히 한 번' 외부 부작용을 무조건 보장한다고 표현하지 않는다.

Webhook은 공급자 검증 절차와 연결 식별을 거쳐 tenant를 결정하고 중복/역순 이벤트를 처리한다. body의 tenant 값을 신뢰하지 않는다. Webhook 미지원 채널은 호출 한도 내 polling과 최근 기간 재대조로 보완한다. 과거자료 초기 수집과 신규 주문 수집의 우선순위를 분리한다.

## 10. 앱 UI 원칙

세부 명세는 `2026-09-07-desktop-business-ui-design.md`를 따른다. 기존 Phase28 공통 디자인과 오늘·주문·CS를 기준으로 삼되, 이번 사용자의 명시적 허용에 따라 앱용 배치를 조정한다. 모바일 시안은 만들지 않는다.

사업장 전환은 색만 바꾸는 동작이 아니다. 선택행/작성중 내용/열린 상세/캐시/구독/다운로드/프린트 미확정 작업을 정리한다. 전환 전 시작된 읽기 응답을 새 사업장 화면에 그리지 않는다. 쓰기 payload는 원래 tenant에 묶이며 UI 전환으로 다시 해석하지 않는다. 진행 중 발급/인쇄는 완료 확인 전 전환을 막거나 명시적으로 정리하도록 한다.

앱은 로컬 업무 데이터를 장기간 복제하지 않는다. 재시작 시 세션과 멤버십을 확인한 후 마지막 접근 가능 사업장을 연다. 권한을 잃었으면 민감한 이전 화면을 먼저 보여주지 않는다. Windows 알림은 선택 기능이며 기본적으로 고객 개인정보를 넣지 않는다. 휴대폰 알림은 제외한다.

## 11. 기존 하린식품 이전과 철회

1. 실제 스키마·route·worker·bucket·view·RPC·cache·env 전체 인벤토리를 작성한다.
2. 백업과 별도 환경 복구를 검증하고 하린식품 tenant 및 기존 사용자 매핑을 준비한다.
3. nullable tenant 열과 새 제약/인덱스를 먼저 추가한다. 데이터 소유가 불명확한 행은 격리 목록에 남기고 임의 배정하지 않는다.
4. 신규 쓰기가 누락되지 않도록 단일 쓰기 소유자를 정한다. 이전 중 하린식품 레거시 경로에만 한정한 호환 할당을 두고 신규 경로의 tenant 누락은 거부한다.
5. 기존 행을 배치 backfill하며 건수·ID 집합·합계·상태·원천 hash·부모자식 소유를 비교한다. 읽기 shadow 비교는 가능하나 외부 발급/전송을 양쪽에서 실행하지 않는다.
6. 인덱스/복합 unique/upsert를 함께 바꾸고 NOT NULL 및 참조 제약을 검증한다. 짧은 전환 구간에 필요한 쓰기 정지는 사전 안내한다.
7. 하린식품만 tenant 경로로 전환해 검수한 뒤, 빈 듀모르 테스트 사업장을 열어 격리 시험한다. 합격 후 듀모르 소유자 승인으로 실연결한다.
8. 사용 흔적·누락 경로 0과 안정 관찰 후에만 전역 계정 fallback/구 경로를 제거한다. 레거시 환경변수 제거는 전체 consumer 전환과 복구 계획 검증 뒤에 한다.

두 번째 실사업장 진입 후에는 tenant를 모르는 이전 서버 버전으로 롤백하지 않는다. 테넌트 인식 호환 버전/사업장별 feature flag로 복귀한다. 전체 DB 복원은 다른 사업장의 최신 주문을 되돌리므로 일반 UI 롤백 수단으로 쓰지 않는다. 백업을 격리 환경에 복원하고 대상 사업장의 필요한 자료만 검증·반영하는 복구 절차를 마련한다.

## 12. 데이터 처리·운영 준비

외부 사업장 도입 전 데이터 처리 범위, 서버 위치/재위탁 서비스, 접근 기록, 탈퇴·보존·삭제·export 정책, 침해 대응 담당을 문서화하고 필요한 검토를 받는다. 본 문서는 법률 준수 완료 판정이 아니다. 보존기간 숫자는 관할/계약/업무 검토 없이 확정하지 않는다.

사업장 비활성화는 로그인/수집/실행 정지이고 삭제와 구분한다. 소유자 재인증 및 삭제 유예/보존 예외/백업 만료를 설명한 후 정해진 절차로 처리한다. 파일 signed URL은 짧은 수명으로 제한하고 이미 내보낸 파일을 원격으로 회수할 수 있다고 약속하지 않는다.

사업장별 저장량/API 호출/AI 비용/실패율/수집 지연을 기록한다. 내부 쿼터는 제공자의 공식 한도와 실제 부하 검증으로 산정하며, Supabase Pro를 사용한다는 이유만으로 다사업장 보안·성능이 자동 해결된다고 하지 않는다.

## 13. 출시 차단 조건

다른 사업장의 데이터/알림/파일 노출, 타 사업장 API 키 사용, 승인 밖 외부 쓰기, 금액 불일치, 중복 발급, 로그인 불능, 이전 누락이 한 건이라도 재현되면 실사용 확대를 중단한다. '한 번에 오류 없음'을 보장하지 않고, 실패 재현·방어·관측·복구 증거로 출시 여부를 판정한다.
