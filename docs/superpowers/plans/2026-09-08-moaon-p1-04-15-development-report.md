# 모아온 P1-04-15 개발 보고서

## 이번 개발

기존 인증 요청 제한 로직은 신뢰할 수 있는 접속 IP를 전달받아야 작동한다. 이번에는 Vercel 직접 접속 환경에 한정해 요청에서 그 IP를 검증하고 기존 제한 로직으로 연결하는 내부 부품을 추가한다. 새로운 공개 로그인 경로·화면을 여는 작업은 아니다.

## 적용할 동작

1. 서버가 Vercel production이고 직접 접속 방식으로 명시됐는지 확인한다.
2. Vercel 전용 IP와 전달 IP가 하나의 동일한 주소를 뜻하는지 검사한다. 여러 IP가 섞였거나 없거나 다르면 임의로 첫 번째 값을 고르지 않는다.
3. IP·전체 요청 제한을 먼저 확인하고, 허용된 경우에만 계정별 요청 제한을 진행한다.
4. IP·키·계정 원문은 제한 DB에 넘기지 않고 기존 HMAC 처리기를 재사용한다. 원본 IP를 오류나 로그로 남기지 않는다.
5. 대기 중 취소되면 다음 요청을 시작하지 않는다. 이미 전달한 DB 요청의 취소나 카운터 복구를 보장하지 않는다.

## 범위 판단

- 직접 Vercel 접속만 지원하며 공개 연결은 아직 하지 않는다. 헤더 값이 맞다는 것만으로 서버의 진위를 증명할 수 없기 때문이다. 실제 요청 위조·외부 프록시 확인이 끝나야 활성화할 수 있다. 외부 프록시를 사용한다면 별도 연결 작업이 필요하다.
- 기존 호출별 제한 시간을 유지한다. 두 DB 호출이 순서대로 각각 제한 시간을 사용할 수 있으므로 전체 작업 시간이 그중 한 번의 제한과 같다고 안내하면 안 된다.

[Vercel 공식 요청 헤더 문서](https://vercel.com/docs/headers/request-headers)를 2026-09-08 확인했다. 이 문서의 헤더 규약을 구현 근거로 사용했지만 문서를 읽거나 합성 요청을 시험한 것이 실제 운영 헤더 검증을 대신하지 않는다.

## 검증 기록

시작 소스8bb992f, 전체 기준 검사2,508/2,508(59.02초, 실패·취소·건너뜀0). 구현61b0bbb의 집중 회귀68/68, 문법·diff 검사가 통과했다. 모듈 미구현 상태의 실패를 확인한 뒤 구현했으며, 자체 검토에서 함수의 bind 속성을 읽는 위험을 실패 테스트로 확인하고 Reflect.apply 호출로 수정했다.

새 테스트는 native Request와 실제 기존 admission·authenticateAccount 함수를 실행하되 RPC·인증 공급자·프로필 저장은 합성 대역이다. 실제 운영 DB나 Vercel 접속 헤더가 검증됐다는 뜻은 아니다. invalid ingress와 한도 거절에서 프로필 조회·공급자 인증·세션 저장이 호출되지 않는지 확인한다. 독립 검토·빌드·최종 전체·배포 결과는 확인 후 기록한다.

## 다음 순서와 미완료 사항

실제 접속 경로에서 위조 헤더가 덮어써지는지와 직접 접속 조건을 검증하고, 지정된 인증 환경의 키·DB 권한·MFA를 연결 시험한다. 기존 로그인 회귀와 실패 안내를 통과하기 전 새 공개 인증을 연결하지 않는다. 사업장별 데이터 격리(P2), 앱 UI(P4), Windows EXE(P5)는 별도 후속 단계다.

신규 유료 자원·DB 테스트 브랜치·실계정 비밀번호 입력·메일 발송·운영 데이터 복사는 하지 않는다. 기존 서비스 사용량 과금 자체를 0원으로 보증하지는 않는다.
