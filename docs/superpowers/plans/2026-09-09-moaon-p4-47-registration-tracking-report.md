# P4-47 — 송장 등록 후 배송추적 연결

2026-09-09 / 모아온 0.32.0

## 사용자가 할 수 있게 된 일

자동 발급·등록 또는 이미 발급된 송장 등록에서 서버가 등록 성공을 확인하면, 같은 주문·송장에 배송추적 조회 작업을 요청한다. 기존 웹 허브의 API를 재사용하며 웹 화면을 앱에 삽입하지 않는다. DB·서버·IP·요금제는 변경하지 않았다.

지원 범위는 현재 앱에서 등록 가능한 Cafe24와 쿠팡 판매자배송이다. 네이버 및 로켓그로스의 직접 등록 지원을 이번 작업으로 확장한 것은 아니다.

## 개발 내역

- 등록 후 서버를 다시 읽어 주문 동일성·송장 번호·등록 상태를 확인한 뒤에만 `POST /api/shipping/tracking`을 실행한다.
- 본문은 선택된 한 주문의 `orderIds`와 `mode: automatic`만 전송한다. 빈 선택으로 전체 주문을 갱신하지 않는다.
- 기존 서버의 5분 자동 작업 중복 방지 정책을 재사용한다. 새로운 스케줄러나 유료 인프라를 만들지 않는다.
- 추적 오류·시간 초과는 등록 실패로 바꾸지 않는다. 이미 성공한 송장을 재발급하거나 플랫폼에 재전송하지 않는다.
- 실제 실행 확인창에 등록 후 배송추적 요청이 이어진다는 설명을 추가했다.
- 취소 주문, 플랫폼/주문 ID 불일치, 원본 주문 식별 불명, 송장 변경은 추적 요청을 차단한다. 로그아웃 뒤 늦은 응답은 노출하지 않는다.

## UI 디테일

- 등록 결과 안에 ‘배송추적 요청 접수 · 완료 아님’ 또는 ‘송장 등록 완료 · 배송추적 확인 필요’를 따로 표시한다.
- ‘주문·추적 열기’로 해당 주문 상세에 이동한다. 상세를 여는 것만으로 반복 조회하지 않는다.
- 저장된 유효한 추적 상태를 확인한 경우 ‘주문 목록 다시 조회’를 제공한다. 대기 상태에서는 숨기며, 앱이 임의로 주문을 배송완료로 바꾸지 않는다.
- 추적 안내와 이동 버튼은 결과 행 안에서 줄바꿈되도록 배치해 좁은 창에서도 겹치지 않게 했다. 기존 패널 접힘과 스크롤 기능은 유지한다.

## 검증 증거

- 실패하는 UI 시험을 먼저 확인한 뒤 구현하고 재통과했다.
- 앱 단위 테스트 177/177 통과. 실제 전송 경계를 모의 응답으로 검증했다.
- 자동 발급·등록, 수동 등록, 배송추적 UI 시험: 개발 코드와 패키지 `app.asar` 각각 통과. 격리 프로필과 개발용 Electron 실행기로 패키지 코드를 검증했다.
- 별도 읽기 전용 코드 리뷰에서 신규 결함 없음. 관련 28개 시험 재통과.
- Windows NSIS 0.32.0 빌드 성공, 이 PC 설치 종료 코드 0.
- 설치 EXE 두 번 재실행에서 저장 로그인 유지. 업무 화면 진입 3.150초/2.312초는 해당 실행 측정이며 속도 보장이 아니다. 네 주문 구간과 완료 주문 페이지 이동은 실제 서버 읽기로 통과했다.
- 설치본 열 정렬 오차 0px, 패널 접힘 21프레임, 내용 유지·접힌 패널 비활성·스크롤바 숨김 확인.
- 운영 주문 발급, 플랫폼 송장 전송, 실제 배송추적 POST, 물리 인쇄는 시험으로 실행하지 않았다. 따라서 실제 출고 전체 과정 완료를 주장하지 않는다.

## 다음 단계 — P4-48

주문 화면을 유지하며 기존 웹 허브의 신규 주문 수집 경로를 앱에 연결하는 작업을 진행한다. 채널별 수집 진행/실패/최종 확인 시각을 구분하고, 수집 완료 후 목록 재조회로 연결한다. 저장 목록 새로고침과 플랫폼 신규 수집이 다른 작업임을 UI에서 분명히 한다. 중복 클릭·부분 실패·로그아웃·느린 응답을 검증한 뒤 인도한다.

일괄 출력/내보내기와 실제 출고용 PC의 우체국 발급→플랫폼 등록→라벨 출력 인수는 남아 있다. 주문 페이지의 필수 기능 인수 이후 오늘·운영·분석·캘린더·설정 순으로 이식한다.

복구는 이전 0.31.0 설치본으로 가능하다. 이번 변경에 DB 마이그레이션은 없으며, 추적 실패를 이유로 기존 송장 기록을 삭제하지 않는다.
