# P4-61G 서버 자격증명 저장 트랜잭션 후보

## 구현

- 비공개 control 스키마에 사업장·플랫폼 복합키, revision, 암호문, 변경 사용자·시각을 저장하는 테이블 후보를 추가했다. 실제 운영 마이그레이션이 아니다.
- 서버가 주입한 verifySession을 사용해 사용자 신원을 확인한다. 트랜잭션 안에서 사업장과 회원 행을 잠그고 ACTIVE OWNER만 저장한다.
- expectedRevision을 현재 DB와 비교하여 오래된 설정 덮어쓰기를 거부한다. 새 revision에 묶인 암호문만 저장하며 반환은 식별자·revision·미검증 상태뿐이다.
- 저장 직후 세션을 다시 검증하고 사용자·세션 동일성 및 DB 시각 기준 만료를 확인한다. 실패하면 전체 트랜잭션을 롤백한다.
- RLS 활성화, public/anon/authenticated 접근 제거. 운영 서버 역할의 최소 권한과 정책은 아직 연결하지 않았다. 테스트의 DB 관리자 권한으로 운영 준비를 증명하지 않는다.

## 검증

정식 npm test 전체 2,680/2,680 통과. 새 저장 시험의 실패 확인 후 구현했다.

격리 PGlite PostgreSQL에서 실제 SQL과 암호화 모듈을 사용했다. 외부 세션 검증만 시험 어댑터다. 저장 원문 비노출·복호화 결과, 다른 사업장·위조 role·비소유자 거부, stale revision, 세션 거절 롤백, 두 저장 요청 중 하나만 성공, 일반 역할 접근 거부를 검증한다. PGlite는 단일 연결이므로 다중 PostgreSQL 연결의 경합 시험은 별도 필요하다.

## 남은 경계

세션 재확인은 인증 저장소와 같은 트랜잭션 잠금이 아니다. 최종 검증 직후 발생하는 폐기까지 엄격하게 막는 세션 fence 통합은 남아 있다. 공급자별 필수 필드 검증·감사 이력, 서버 런타임 역할, 저장 HTTP API·앱 연결·실제 플랫폼 인증 역시 남아 있다.

운영 DB·키·서버에 적용하지 않았다. 앱 UI 및 설치 버전 0.51.2는 변경하지 않았다.

Supabase 스킬과 [공식 RLS 문서](https://supabase.com/docs/guides/database/postgres/row-level-security)에 따라 공개 역할 차단과 RLS를 함께 검토했다. changelog.md는 웹 도구의 markdown 콘텐츠 형식 오류로 읽지 못했다. 새 Supabase SDK/API에는 의존하지 않는다.
