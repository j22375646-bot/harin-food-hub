# 모아온 P1-04-6 개발 보고서

> 진행 중: IP별·서비스 전체 인증 요청 제한 기반. 최종 검증·배포 결과는 완료 후 기록한다. 기존 운영 로그인에는 활성화하지 않는다.

## 이번에 만드는 것

여러 사업장이 사용하는 모아온에서는 누군가 아이디를 계속 바꾸며 로그인을 시도할 수도 있다. 지난 단계의 계정별 제한만으로는 이런 요청 전체를 제한하지 못한다. 이번에는 계정별 확인 앞에 같은 IP와 서비스 전체 요청량을 확인하는 공통 제한을 추가한다.

요청 순서는 서비스 전체 → IP → 기존 계정별 제한 → 인증 처리다. 앞 단계에서 거절되거나 저장소가 응답하지 않으면 인증 처리로 넘어가지 않는다. 앞 단계에서 쓴 횟수는 뒤 단계의 거절로 돌려주지 않는 보수적인 방식이며, 세 단계를 한 번에 처리하는 단일 거래는 아니다.

| 범위 | 후보 기준 | 의미 |
| --- | --- | --- |
| 같은 IP | 5분 30회 | 여러 아이디를 바꾸어도 IP가 같으면 함께 계산 |
| 서비스 전체 | 5분 500회 | 여러 IP에서 들어오는 요청도 합산 |
| 계정별 | 이전 단계 정책 유지 | 로그인·복구·이메일 확인별 추가 제한 |

이 숫자는 실제 이용량에 맞춘 최종 운영 설정이 아니다. 사무실의 여러 PC는 하나의 IP를 공유할 수 있으며, 전체 제한은 공격 중 정상 사용자까지 차단할 수 있다. 실제 전환 전 정책 조정과 관측이 필요하다.

IP 원문 대신 서버 비밀키로 계산한 식별값을 사용한다. 이는 원문 저장을 줄이는 조치이지 완전한 익명화라는 뜻은 아니다. 서버가 확인한 IP만 받도록 만들며, 사용자가 보낸 임의의 헤더를 신뢰하는 연결은 이번에 추가하지 않는다.

## 검증 기록

- 시작 기준: `6f28e017c4afe47764da9519ab720b56d3d1eb5a`.
- 변경 전 전체 검사: 2,205/2,205 통과, 실패·취소·건너뜀 0.
- 기존 로컬 PostgreSQL을 `127.0.0.1:55437`에만 열어 재사용한다. 새 유료 서비스나 운영 데이터 복사본은 만들지 않는다.
- 기존 계정별 제한의 실제 PostgreSQL 재검사 2/2 통과: 서로 다른 DB 연결에서 잠금 대기, 20건 중 정확히 10건 허용, 롤백 후 복원을 확인했다.
- 배포 전 운영 1.47.0 확인: `/login` 200, `/orders` 307 로그인 이동, `/api/orders/page`와 `/api/navigation/operation-snapshot` 각각 401. 비밀번호 입력 없이 접근 보호만 확인했다.
- 구현 전 새 모듈이 없어 검사가 실패하는 것을 확인한 후 구현했다. 구현 후 신규 집중 11/11, 로그인·복구 관련 회귀 68/68, 전체 2,216/2,216 통과를 기록했다.
- 실제 PostgreSQL 신규 동시 요청 검사 3/3 통과: 같은 IP 40건 중 30건, 여러 IP 501건 중 500건만 허용했다. 서로 다른 DB 연결의 잠금 대기와 롤백 후 두 제한 복원도 확인했다.
- 전체 검사에는 기존 모듈 형식 경고와 오류 상황 검사용 진단 출력이 있다. 실패는 없지만 경고가 전혀 없는 출력으로 표현하지 않는다.
- 독립 검토, 최종 빌드 및 배포는 아직 진행 중이다.

## 운영 적용과 남은 개발

기존 로그인·UI·비밀번호·채널 업무 API를 유지한다. 후보 SQL을 운영 DB에 적용하거나 새 가입 기능을 개방하지 않는다. 지금 사용할 수 있는 EXE를 만드는 단계도 아니다.

다음 인증 준비에서는 만료 제한 기록 정리·보관 정책과 아이디/이메일이 같은 계정으로 연결되는 기준을 보완한다. 이후 운영자 복구 검토·안전한 해결 절차, 실제 Auth/메일/HTTP 시험을 거쳐야 한다. 업무 자료의 사업장별 격리(P2), 각 사업장의 플랫폼 연결(P3), 앱 UI(P4), Windows EXE·프린터(P5)는 전체 계획에 그대로 남아 있다.
