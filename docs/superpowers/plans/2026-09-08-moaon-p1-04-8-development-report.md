# 모아온 P1-04-8 개발 보고서

## 현재 작업 범위

비밀번호 복구 중 연결이 끊기면 실제 변경 여부와 화면의 처리 이력이 다를 수 있다. 이번 단계는 **확실한 DB 근거가 있는 이력만 정리하는 서버 기반**이다. 계정 잠금을 강제로 풀거나 비밀번호를 다시 바꾸는 기능이 아니다.

| 확인된 근거 | 허용할 처리 |
|---|---|
| 비밀번호 변경 완료 기록이 있고 계정 잠금 없음 | 검토 이력을 완료로 정리 |
| 해당 변경이 시작되지 않았고 계정 잠금 없음 | 검토 이력을 미실행 종료로 정리 |
| 진행 중·잠김·자료 불일치·대상 비활성 | 보류 유지, 강제 처리 금지 |
| 이미 정리한 같은 요청을 다시 실행 | 기존 처리 결과 반환, 중복 이력 금지 |

일반 사업장 관리자를 복구 운영자로 간주하지 않는다. 내부 운영자 목록은 처음에 비어 있으며, 추후 별도 검증을 거쳐 지정해야 한다. 화면에서 다른 계정 번호나 운영자 번호를 넣는 것만으로 권한이 생기지 않도록 서버 연결부와 DB 검사 모두 필요하다.

## 활성화 범위

이번 산출물은 새 계정 체계의 **비활성 후보 코드**다. 운영 DB에 새 SQL을 적용하거나 새 로그인·메일·복구 화면을 열지 않는다. 기존 로그인, 비밀번호, 화면, 주문·정산 API는 그대로 유지한다. 운영자 로그인과 HTTP 신뢰 경계, 실제 Auth/메일 검증은 다음 단계에 남는다.

## 개발 중 판단

1. 설계 초안의 계정 참조 이름을 실제 기존 기본키 `dashboard_users.user_id`에 맞췄다. 기존 계정 테이블 구조는 바꾸지 않는다. 이 판단이 틀리면 새 후보 SQL 설치가 실패하므로 설치 검사로 확인한다.
2. 복구 운영자 목록은 읽기 권한만 주고, 권한 회수와 검토가 동시에 진행되지 않도록 별도 DB 잠금을 사용한다. 수정 권한을 추가하는 대신 선택한 방식이다. 운영자 목록 변경이 진행 중인 검토를 기다릴 수 있다는 비용이 있으며 실제 동시 실행 검사로 확인한다.
3. 오래된 DB 조회 상태로 권한을 계속 인정하지 않도록 이번 RPC는 최신 조회 방식인 `READ COMMITTED`에서만 허용한다. 다른 트랜잭션 방식은 차단한다. 이후 연결 환경이 다른 방식을 사용하면 복구 검토를 이용할 수 없으므로 활성화 전에 이 조건을 확인해야 한다.
