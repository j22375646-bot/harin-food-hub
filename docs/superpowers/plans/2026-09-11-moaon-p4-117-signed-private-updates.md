# P4-117 · 유료 인증서 없는 공개키 검증 업데이트 (0.103.0)

## 완료 범위

유료 Windows 코드서명/Artifact Signing 없이 Ed25519 전용 배포 서명과 앱 내 공개키 검증으로 전환했다.0.103.0 설치파일과 검증 메타데이터를 기존 공개 GitHub 저장소의 `moaon-stable` 전용 릴리스에 게시했다. 저장소 가시성을 바꾸거나 새 유료 서비스를 만들지 않았다. 이후 코드 수정만으로 고객 업데이트가 되지는 않으며 검증·빌드·서명·릴리스 게시를 거친 버전이 앱에 나타난다.

전달 링크: https://github.com/j22375646-bot/harin-food-hub/releases/download/moaon-stable/Moaon-0.103.0-Setup.exe

릴리스: https://github.com/j22375646-bot/harin-food-hub/releases/tag/moaon-stable

## 처음 설치 및 이후 업데이트

- 사장님 PC에는0.103.0 설치파일을 처음 한 번 전달·설치하고 사업장 권한으로 로그인한다. 기존0.102.0 이하 파일은 업데이트 연결이 꺼져 있으므로 새 설치파일을 한 번 직접 설치해야 한다.
- 이후 앱 시작 후/6시간마다 배포 버전을 확인하고 새 버전이면 다운로드 동의를 묻는다. 나중에/진행률/작업 계속하기/저장 후 재시작을 유지한다. 처리 중 작업과 열린 자식 창에서는 재시작을 차단한다.
- Windows Authenticode 서명은 `NotSigned`다. 전용 배포 서명은 앱이 업데이트를 검증하는 장치이며 Windows의 알 수 없는 게시자 경고를 없애지는 않는다. 회사 PC의 보안 정책이 설치를 막을 수 있으며 사장님 PC의 실제 설치·로그인·프린터 인수는 별도다.

## 검증 구조

`release.json`의 정확한 payload 바이트를 Ed25519로 서명한다. 앱 ID, stable 채널, 버전, 고정 형식 설치파일 이름, 바이트 수, SHA512를 서명에 포함한다. 앱에 고정된 공개키로 서명을 확인하고 `latest.yml`의 버전·파일·해시·크기와 일치해야 다운로드를 허용한다. 웹 설치 패키지와 임의 다운로드 파일/경로를 거부한다.

기존 electron-updater의 NSIS 전송/설치를 사용하되 다운로드 완료 이벤트를 직접 전달하지 않는다. 신규/캐시 설치파일 모두 서명된 해시와 크기를 재검증한 다음에만 준비 완료를 알린다. 설치 직전에도 파일 해시와 실제 설치 경로를 다시 확인한다. 유료 서명 검사를 단순히 끄는 것과 구분된다.

## 키와 배포 절차

개인키는 `D:\GPT\secrets\moaon-update\private.dpapi`에 Windows 현재 계정 DPAPI로 암호화해 보관한다. 저장소·설치파일에는 개인키를 포함하지 않으며 공개키만 포함한다. 키를 잃거나 PC/Windows 계정을 교체하면 키 이전/신뢰키 교체 계획이 필요하므로 해당 파일을 임의 삭제하지 않는다. DPAPI 파일만 다른 계정으로 복사해서 사용할 수는 없다.

1. `desktop/scripts/build-distribution.ps1`: 현재 공개키 채널을 포함한 NSIS 빌드 → DPAPI 개인키로 release.json 서명 → latest.yml 생성. 서명 실패는 배포 실패로 처리한다.
2. 코드/파일 일치·화면 검증 이후 `node desktop/scripts/publish-signed-release.cjs <산출물 폴더>`로 전용 릴리스에 설치파일을 먼저 올리고 서명 메타데이터와 latest.yml을 게시한다. 기존 GitHub 자격증명은 메모리에서만 사용하며 파일/앱/출력에 넣지 않는다. 업무 데이터나 사용자 프로필은 업로드하지 않는다.
3. 같은 버전 설치파일 덮어쓰기를 차단한다. 배포 이상을 복구할 때에도 더 높은 버전으로 수정 배포한다. 중간 게시 실패에서 메타데이터 불일치는 클라이언트가 거부하므로 새로 확인하도록 한다.
