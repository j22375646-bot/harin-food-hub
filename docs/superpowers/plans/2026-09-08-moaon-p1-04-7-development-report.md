# 모아온 P1-04-7 개발 보고서

> 구현 완료·배포 검증 대기: 인증 제한 기록 정리와 동일 계정 로그인 횟수 합산. 운영 로그인·UI·업무 기능은 유지하며 새 기능은 미활성 후보다.

## 사용자 관점의 변경

### 오래된 제한 기록 정리

짧은 시간 동안 로그인 요청을 셀 때 쓰는 기록이 계속 쌓이지 않도록 정리할 수 있는 서버 기능을 만든다. 기준은 DB가 기록한 창 시작 시각으로부터 24시간 초과다. 한 번에 대상별 기록 500개, IP 기록 500개까지만 처리하고 다음 호출에서 나머지를 처리한다.

사용 중인 기록은 건너뛰고, 서비스 전체 제한 행은 남긴다. 주문·정산·회원·세션·비밀번호 복구 이력은 삭제 대상이 아니다. 아직 운영 정리 스케줄러를 켜는 단계는 아니다.

### 아이디와 이메일의 로그인 제한 합산

같은 사람이 아이디로 로그인하다가 이메일로 바꾸어 입력해도 같은 계정이라면 횟수를 함께 센다. 입력 문자열의 사전 제한은 그대로 두고, 서버에서 확인한 계정 ID에 추가로 제한을 적용한다. 다른 계정끼리 비슷한 이메일이라고 합치지 않는다.

이 변경은 로그인 제한의 동일 계정 판별이며, 중복 계정 병합이나 모든 이메일 변경 흐름을 완성한다는 뜻은 아니다. 기존 로그인에는 명시적으로 연결하지 않는 한 동작하지 않는다.

향후 활성화 시 `auth-request-limit.sql`, `auth-request-admission.sql`, `auth-request-retention.sql` 세 후보를 함께 설치·검증한 후 정리 스케줄러를 연결해야 한다. 정리 SQL만 먼저 켜지 않는다.

## 개발 중 판단한 사항

요청을 아직 한 번도 세지 않은 기록은 실제로 잠금을 얻은 뒤 첫 요청 시각부터 제한 시간을 시작하도록 정했다. 미래 시각 기록과 이미 사용 중인 기록의 기존 제한은 유지한다. DB 내부 튜플 상태에 의존하는 방식은 사용하지 않았다. 이 판단이 맞지 않으면 미리 만들어 둔 미사용 기록의 제한 종료가 기존 삽입 시각 기준보다 조금 늦어질 수 있다. 실제 DB의 삭제·요청 동시 실행과 미래 시각 회귀 검사로 확인했으며 운영에는 아직 켜지 않았다.

## 이후 순서

다음 구현 단위는 **P1-04-8 운영자 복구 검토·해결 기반**으로 잡는다. 비밀번호 복구 결과가 불명확할 때 자동으로 성공 처리하거나 잠금을 풀지 않고, 저장된 처리 근거를 확인해 안전하게 해결하는 절차다. 중복 클릭·동시 처리·다른 계정 작업 혼입·오래된 결과 적용을 막는 검사가 필요하다. 실제 비밀번호 변경이나 운영 잠금 해제는 이 기반 구현과 별도 검증한다.

그 뒤 실제 Auth/메일/HTTP·IP 신뢰 경계 검증, 제한 한도 조정과 정리 스케줄러 연결이 남아 있다. 이후 사업장 자료 격리(P2), 플랫폼 연결(P3), 앱 UI(P4), Windows EXE·프린터(P5)를 진행한다. 이번 배포만으로 다사업장 가입이나 설치 프로그램이 개방되지는 않는다.
