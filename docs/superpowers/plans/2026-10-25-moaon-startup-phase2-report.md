# 성능 개선 2단계: 첫 화면과 네이티브 트레이 준비 분리

## 원인과 변경

설치0.202.0의 동일 조건5회 비교에서 createTrayLifecycle 호출이 약1,124~2,662ms 동안 메인 프로세스를 점유했다. 이 호출은 loadURL보다 먼저 실행됐다. 별도 세부 측정에서 setIcon/setAppDetails는 약16.6ms, 블로그 등록과 연결 객체 초기화는 각각1ms 안팎이어서 해당 기능을 무조건 지연 로드하지 않았다.

0.203.0은 닫기·업데이트·Windows 종료 보호를 즉시 등록하고 첫 ready-to-show 이후250ms에 네이티브 트레이를 준비한다. 준비 중 상태 변경은 저장해 트레이로 전달한다. 준비 전 닫기, 모달, 업데이트 설치, 종료, 늦은 콜백, 생성 실패도 처리한다. 실패하면서 창이 숨겨져 있으면 포커스를 가져오지 않고 다시 표시한다.

트레이 네이티브 비용 자체가 사라지는 변경은 아니다. 이를 첫 화면의 선행 작업에서 분리했으며, 이후 짧은 메인 처리 지연 가능성은 남는다. 이번 단계는 서버 조회·수집·발급 동시성 또는 렌더링 목록 로직을 바꾸지 않는다.

## 검증

- 단위/회귀 시험528개 통과: connection/issue-register158개, 나머지370개. 최초 무제한 전체 실행은 종료하고 해당 두 그룹으로 다시 완료했다. 실패를 무시한 합산이 아니다.
- deferred-tray7개에는 실제 createTrayLifecycle 조합을 통한 리스너 인계·복원·종료도 포함한다.
- 별도 검토에서 배포를 막는 회귀가 발견되지 않았다. 권장된 조합 시험을 추가했다.
- 자동 검증 bootstrap의 이후 ready-to-show 창 배치도 오른쪽 보조 모니터를 유지하도록 수정했다. 메인 모니터를 지정하던 tray-native-smoke도 오른쪽으로 바꿨다.
- 설치패키지 전체164개 파일 일치: app.asar SHA256 d891a2c12bd2fb41719e125755cafbbebdb26dbe075288de3081e17388204e84.
- 설치0.203.0 payload 가시 Electron 시험 PASS: 첫 frame 이후 native Tray 생성, 닫기/복원/종료, 숨김 중 team4회·주문1회·CS1회 모의 조회 확인. 실제 계정 인증 및 운영 주문 작업은 실행하지 않았다.

## 성능 비교 범위

구/신 설치 app.asar 각각5회, 동일 Electron·격리 프로필·원격401모의 응답·업데이트 중지 조건으로 비교했다. 실제 사용자의 인증 세션이나 운영 주문 속도 검증이 아니며 OS cold-cache는 제어하지 않았다. 구버전 다음 신버전 순서여서 디스크/PC 부하의 시간 편향 가능성도 있다.

- 0.202.0 shell 준비 중앙값4,291.6ms, 범위3,503.8~7,026.9ms.
- 0.203.0 shell 준비 중앙값3,451.8ms, 범위2,791.3~4,178.9ms. 수치는 최종 summary.json과 대조한다.
- 관측 중앙값 약0.84초(약20%) 감소. 모든 실행이나 실제 로그인 완료에 같은 개선을 보장하지 않는다. 작은 표본의 최댓값을 장기 p95 보장으로 사용하지 않는다.
