# P4-54 설치본 실제 주문 조회 인수

## 이번에 실제로 확인한 결과

0.38.8 설치 앱을 정상 종료 후 재실행했다. 로그인 유지 및 실제 주문 UI 검사 PASS. 열 중심 오차0px, 상세 패널 접힘22개 중간 프레임, 접힘 후 내용 유지·inert·화면 밖 이동, scrollbar none 확인. 비밀번호 입력·쿠키 삭제·실제 송장 쓰기는 하지 않았다.

인증된 설치 앱의 기존 IPC 경로로 순차 조회한 결과:

| 구간 | 응답 | 전체/조회 건수 | 확인 내용 |
|---|---|---|---|
| 발급 전 | READY | 전체2/조회2 | NAVER2, 자동 발급 가능0 |
| 등록 후 | READY | 전체0/조회0 | 현재 저장 목록에 없음 |
| 배송중 | READY | 전체0/조회0 | 현재 저장 목록에 없음 |
| 완료·취소 | READY | 전체89/조회20 | NAVER15, COUPANG4, CAFE241 |
| 서버 등록 이력 | READY | 조회25 | REGISTERED25 |
| 미완료 로컬 출고 | READY | 조회0 | 복원할 기록 없음 |

서버 이력25건은 기존 저장된 성공 기록이다. 이번 앱으로 신규 등록25건을 실행했거나 판매 플랫폼 원장과 전부 대조했다는 뜻이 아니다. 목록의 0건은 이 조회 시점 결과이며 플랫폼 전체 원장의 부재를 보장하지 않는다.

## 다음 작업을 막던 실제 조건

로그인 장애는 이번 검사에서 해소되어 실조회까지 진행했다. 현재 발급 전 주문은 네이버만 있다. 기존 웹 서버 `app/api/shipping/actions/route.js`도 네이버를 허브 출고에서 제외하며 Cafe24/쿠팡만 분기한다. `lib/epost/dispatch-guard.js` 역시 두 채널만 허용한다. 따라서 단순 앱 이식 누락으로 보고 네이버 제한만 풀어서는 안 된다.

기존 설계를 유지하면 실제 신규 발급·등록 인수에는 유효한 Cafe24 또는 쿠팡 판매자배송 시험 주문과 정상 송장이 필요하다. 네이버까지 허브 직접 출고로 바꾸는 것은 기존 웹 기능 복사를 넘어서는 별도 연결 개발이다. 사용자의 기존 승인 없이 고객 주문을 시험용으로 변경하지 않았다.

## 개발계획 반영

1. 로그인 유지 및 설치본 실제 주문 조회/UI 검사는 이번 결과로 PASS 갱신한다.
2. 지원 채널의 시험 주문 확보와 플랫폼 실제 등록 인수는 미완료로 유지한다. 로그인 불가로 계속 표시하지 않는다.
3. 네이버 출고는 기존 서버의 의도적 제외 정책을 유지하고 지원 범위를 문서화한다. 단순 허용목록 변경으로 지원 완료 처리하지 않는다.
4. 주문 페이지 전체 완료나 다른 페이지 개발 시작으로 표시하지 않는다.

이번에는 운영 코드·설치 버전·DB를 변경하지 않고 실환경 검증과 원인 확인을 수행했다.
