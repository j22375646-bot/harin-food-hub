# 모아온 성능 개선 개발계획

> **For agentic workers:** Use superpowers:executing-plans to implement this plan task-by-task. 사용자 착수 지시 전에는 구현·배포하지 않는다.

**Goal:** 시작·주문 전환·선택의 대기를 줄이면서 주문 정확성, 개인화 격리와 진행 중 송장 작업을 보존한다.

**Architecture:** 로컬 표시, 원격 읽기, 수집·발급 작업을 별도 수명주기로 유지한다. 기존 캐시·delta·조회 중복 방지 기능을 확장하며 전면 재작성하지 않는다. 서버에서는 목록 응답 크기뿐 아니라 DB에서 읽는 범위를 줄인다.

**Tech Stack:** Electron, 일반 JavaScript renderer/IPC, Next.js API, Supabase/Postgres.

**Spec:** 이 문서의 근거·범위·완료 기준 및 사용자의 성능 원인 조사/개발계획 요청.

- 코드 변경 없음. 이번 단계는 진단과 계획이다.

- 실사용 MoaonPreview 프로세스5개 working set 합계 약528MiB. Chromium의 공유 메모리를 포함한 단일 스냅샷이므로 고유 RAM·누수 증거가 아니다.
- index.html에 스크립트52개, 스타일25개가 초기 포함된다. 파싱/초기화 비용 후보이며 파일 개수만으로 병목 확정 불가.

- 주문 화면5분 캐시, 변경분 병합, 인증/사업장 변경 시 폐기, 중복 조회 방지 이미 존재한다. 캐시 부재로 진단하지 않는다.
- background-monitor: team READ는 약15초 간격(작업시간 추가), 주문/CS/일정은60초 이상 간격에 순차 조회; 주문수집120초,CS300초. 화면 주문 변경 확인은30초, 송장 상태는 진행 중2초/평시60초. 모든 요청이15초마다 실행되는 것은 아니다.
- 서버 app/api/orders/page/route.js는 loadUnifiedOrders와 이벤트를 읽는다. lib/orders/unified-orders.js는18개 기본 읽기 경로를 병렬 실행하며 일부는 전체 테이블을 페이지 순회하고 raw_data도 읽는다. 화면20건은 DB20건 읽기를 의미하지 않는다. 실제 DB시간/행수/전송량 계측 전 절감률 확정 불가.
- 직전 운영 장애는 DB503/PGRST002와 쿼리 timeout, CPU98%/disk IO balance0%가 함께 관측됐고 재시작 후 계정·세션 조회200/약0.3초로 복구됐다. 장애를 유발한 개별 워크로드는 미확정. 저장공간 부족·결제 만료로 단정하지 않는다.

## 공통 제약 및 검토 항목

- 모든 시험 자료·프로필·로그는 D:\GPT 아래. 실주문 발급/등록/출고를 성능 시험으로 실행하지 않는다.

- 계측 로그에는 비밀번호·쿠키·API키·주소·주문 본문을 남기지 않는다.
- 기존 desktop/test 자동화를 우선하고 가시 검증은 오른쪽 보조 모니터에서 포커스를 가져오지 않는다.
- 아래 수치는 목표이며 현재 보장값이 아니다. 계측 후 같은 PC/같은 데이터로 확정한다. 유료 DB 증설은 별도 비용 승인 없이 실행하지 않는다.

## 5/6. 서버 주문 읽기 범위 축소

대상(서버 저장소): app/api/orders/page/route.js, lib/orders/unified-orders.js, lib/tenancy/workspace-orders-*.js, 필요 시 전용 주문 목록 read-model/마이그레이션.

- [ ] 실제 route와 delta 양쪽의 DB호출/행수/전송량/실행계획을 확인한다. 필요한 Next.js 로컬 가이드와 Supabase 지침을 읽고 수정한다.
- [ ] 목록에 필요한 정규화 필드·상태·총계/버전만 읽는 경로를 만든다. 개인정보/상품 상세/raw_data는 필요한 주문에 한정하되 발급 준비 자료의 사전 수집은 유지한다.
- [ ] 단순 status 필터만 DB로 옮기지 않는다. 추적 기준 배송상태, 묶음/사은품/쿠팡 총금액, 원본 상태 예외를 동일하게 재현해야 한다. 필요하면 쓰기 시 갱신하는 전용 read-model로 좁힌다.
- [ ] 변경분 API는 반환값만 줄이는 수준을 넘어 DB 읽기도 줄인다. 변경 로그에는 tombstone/상태 이동을 포함한다.
- [ ] 검색/총계/페이지 snapshot 정합성과 사업장 격리, backfill/catch-up, 롤백 및 기능 플래그를 함께 설계한다. 서버리스 인스턴스 캐시만 정답 저장소로 사용하지 않는다.
- [ ] 검증: 구/신 목록을 격리 fixture와 읽기 전용 운영 표본으로 대조하고 상태별총계·금액·묶음·추적결과 일치를 확인한다. EXPLAIN과 부하 시험은 격리 DB에서 진행한다.

완료: 주문 조회 p95 50% 개선과 읽기 행/바이트 감소 목표; 정확성 대조 통과. 무료 NANO의 적합성은 개선 후 다시 평가한다.
