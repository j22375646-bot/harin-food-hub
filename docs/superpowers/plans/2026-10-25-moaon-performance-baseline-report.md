# 성능 개선 1단계 측정 결과

## 결과와 한계

설치0.202.0 app.asar를 기존 사용자의 세션과 분리하여 오른쪽 보조 모니터에서 실행했다. 실제 사용자 인증·주문·발급은 사용하지 않았다. 원격 fetch는401로 대체하고 자동 업데이트는 시험에서 중지했다. 따라서 아래 값은 운영 주문/API 성능 또는 실제 설치 EXE 전체 시작 시간의 보장이 아니다.

- 반복10회 shell DOM/bridge 준비: 중앙값4,364ms, p95 5,876ms, 최소3,525ms. OS cold-cache를 제어하지 않아 첫 실행/재실행의 엄격한 cold/warm 비교는 아니다.
- 같은 도구의10초 네트워크 지연 대조: shell3,596ms, shell 이후 인증 조회 대기9,854ms. 서버 지연과 로컬 준비가 분리됨을 확인했다.
- 다른 실행 시점 가시 UI 검증: 샘플20건, 실제 체크박스 클릭100회·탭전환20회·검색20회. 입력 후 두 번의 requestAnimationFrame까지의 시간 p95: 선택34.0ms, 탭50.1ms, 검색33.4ms, 전체재생성33.5ms. 이 값은 실제 물리적 화면 출력 완료 시간이나 실주문20건 성능이 아니다.
- 장시간 누수/실사용 로그인/실서버 쿼리 비용은 아직 측정하지 않았으며 본 결과로 추정하지 않는다.

## 진단 정정과 우선순위

1. 기존20.9초 단일 관측은 반복 고정값이 아니며 이번 기준 중앙값4.36초로 대체한다. 최적화 전후를 비교한 결과가 아니므로 속도가 빨라졌다고 주장하지 않는다.
2. 체크박스 선택은 기존에도 renderSelection만 호출한다. 모든 선택에서 목록을 재생성한다는 설명은 정정한다. 행 클릭은 상세 표시 경로도 있으므로 별도 계측 대상이다.
3. 시작은 창 생성 이후 로딩 완료 사이에 main 지연이 관측된다. 모듈 require 자체 시간은 대부분 짧아, 의존성 개수만 보고 lazy-load를 적용하지 않는다. 다음 단계에서 네이티브 창/아이콘/트레이/세션 준비와 URL load 전후를 더 세분화한다.
4. 서버 주문 조회의 넓은 읽기 범위와 화면·백그라운드 조회 중첩 가능성은 여전히 별도 개선 대상이다. 이번401 시험으로 운영 부하 절감량을 추정하지 않는다.

## 개발 내용과 시험

- performance-baseline.cjs: 반복실행, 고유 D 프로필, 설치 payload, 네트워크 지연 대조, 모의20건 UI 조작, 이벤트 루프 지연/모듈/프로세스 private memory/long task 기록, 경로별 모의 요청 횟수와 결과 저장.
- performance-bootstrap.cjs: 운영 fetch 대체, 자동 업데이트 중지, 시작 이벤트 및90초 자체 종료 제한.
- performance-metrics.cjs와 시험: 최근접 순위p95·중앙값, 입력 유효성, 네트워크 대기 분리.
- launch60초, attached90초, close5초 한도. 종료 타이머는 성공 후 취소하며 생성한 Electron 자식 핸들만 종료한다. 설치된 사용자 앱 프로세스는 대상으로 삼지 않는다.
- 핵심 회귀25/25 통과: delta, freshness, background/tray, 새 계측 계산. 실제 설치 payload를 사용한 가시 시험 통과. 격리 DB 시험은 이번 도구 변경에 해당하지 않는다.
- 도구는 desktop/test에만 추가했으므로 운영 앱 코드/버전 변경과 설치파일 재배포는 하지 않았다. 테스트 계측 추가를 사용자 앱 최적화 배포로 보고하지 않는다.

## 계획 조정 기록

Ruling:1단계의 이번 인수 범위는 재현 가능한 로컬 baseline 확보로 한정한다. 인증된 서버 요청/DB 시간 계측은5단계,30분 장시간 유휴 시험은6단계로 옮긴다. 이유는401 모의 인증에서 오래 기다려도 운영 조회·알림 부하를 재현하지 못하기 때문이다. 비용은 현재 보고서로 서버 속도나 메모리 누수를 판정할 수 없다는 점이며 위 한계에 명시했다.
