# 주문 행 안의 송장 진행 뱃지 및 안전한 이어하기 계획

상태: 1단계 구현·설치 검증·0.198.1 공개 배포 완료. 총 5단계 중 완료 1단계, 남은 4단계. 이전 주문 페이지 5단계 계획은 0.197.0으로 완료됐으며, 아래는 별도 후속 계획이다.

## 사용자 목표

상품명·옵션 아래 작은 뱃지로 각 주문의 현재 송장 단계를 확인한다. 하단의 큰 진행판을 기본 화면에서 없애고, 멈춘 단계의 뱃지를 통해 상태 확인 및 안전한 이어하기를 수행한다. 기존 주문 선택·선택 해제·탭 이동·스크롤 상태를 유지한다.

## 확인한 코드

- 웹허브 `lib/shipping/fulfillment-status.js`: ISSUE/TRANSFER/TRACKING, 대기·실행·재시도 대기·실패 및 표시 문구.
- 웹허브 `app/_phase28/pages/orders-page.js`: 상품 옵션 아래 orderFulfillmentStatus, 작업 활성 시 2초/유휴 시 30초 조회.
- 웹허브 `app/_phase28/pages/orders-page.css`: 활성 점의 1.25초 pulse 및 attention 색상.
- 웹허브 `app/api/shipping/fulfillment-status/route.js`: 서버 작업 기록 조회. 앱에서 사용하기 전 사용자/사업장 범위와 응답 최소화 검증 필요. 현재 경로를 검증 없이 그대로 연결하지 않는다.
- 모아온 `desktop/ui/app.js`: 주문 행은 button이며, 발급 작업·등록 작업 및 복구 목록이 별도 존재한다. 행 내부에 버튼을 중첩하지 않는다.
- 모아온 `desktop/ui/shipping-progress.js`: 현재 작업의 단계 및 45초 무변화 안내. 하단 UI를 행 뱃지 표시로 교체하고 필요한 상태 모델을 분리한다.
- 모아온 `desktop/hub-connection.cjs`, `shipment-registry.cjs`, `shipping-action-journal.cjs`: 기존 요청 조회, 저장된 송장 보존, 재전송 제한을 재사용한다.

## 권장 설계

기본 표시는 주문별 한 줄 뱃지다. 상세는 뱃지를 누를 때 작은 패널로 펼친다. 하단의 큰 진행판과 중복 결과 목록은 기본 화면에서 제거하며 전체 작업 요약은 작은 표시로만 유지한다.

정상 실행은 파랑/보라와 움직이는 점, 대기는 차분한 색, 응답 확인 필요는 정지된 주황, 확인된 실패는 정지된 빨강, 등록 확인 완료는 초록으로 구분한다. 색뿐 아니라 문구·아이콘을 함께 사용하며 reduced-motion 설정을 지킨다.

진행 이벤트, 서버 작업 기록 및 저장된 작업 식별자를 결합한다. 키는 사용자/사업장 범위와 주문 ID 및 작업 식별자에 묶는다. 오래된 이벤트가 새 작업 상태를 덮어쓰지 않게 한다. ISSUE와 TRANSFER/REGISTER 의미를 일치시키되 배송 추적 상태와 쇼핑몰 등록 상태는 구분한다.

## 새 개발 계획: 총 5단계

### 1. 주문 행 뱃지 UI

상품 옵션 아래 단일 뱃지를 추가한다. 현재 단계·채널명을 표시하고 동작 중에만 pulse를 사용한다. 긴 상품명·옵션·여러 건 선택·밝은/어두운 테마에서 배치를 검증한다. 뱃지 클릭이 주문 선택을 반전시키지 않도록 행 구조와 이벤트를 분리한다. 기존 하단 진행판의 중복 표시를 제거한다.

검증: 주문별 다른 단계 표시, 선택 토글 유지, 상세 열기, 작은 창에서 가로 넘침 없음, 마지막 주문이 작업 도구에 가리지 않음.

### 2. 실제 상태 자동 동기화

Main 이벤트로 즉시 반영하고 현재 계정·사업장의 서버 작업 기록을 보완 조회한다. 활성 작업에 한정해 소규모 묶음 조회하며 중첩 요청을 막고 유휴/오류 시 간격을 늘린다. 주문 전체 재조회 대신 바뀐 뱃지만 갱신한다. 페이지 이동 및 앱 재실행 후 기존 작업을 읽어 복원한다. 네트워크 마지막 조회 시각과 서버 마지막 단계 변경 시각을 별도로 보존한다.

검증: 순서가 뒤바뀐 응답, 사업장 전환, 로그아웃, 기존 캐시, 서버 부분 응답, 여러 요청의 교차 상태, 앱 재시작 복원.

### 3. 지연·정체·실패 표시

진행 변화가 없거나 조회가 끊기면 마지막 단계와 경과 시간을 유지하고 애니메이션을 멈춘다. 기본 45초 무변화는 확인 필요의 신호이며 실패 판정이 아니다. 서버가 예정한 자동 재시도 대기는 별도 표시한다. 상세에서 마지막 확인·오류 요약·기존 송장 유무·가능한 다음 동작을 제공한다. 재확인 성공 시 실제 상태에 맞춰 복원한다.

검증: 응답 지연을 실패로 오인하지 않음, 무변화 조회가 경과 시간을 초기화하지 않음, 실패 및 예정된 대기 구별.

### 4. 안전한 상태 확인·이어하기

뱃지 상세에서 우선 기존 요청과 실제 송장·쇼핑몰 상태를 확인한다. 계속 실행 중이면 새 요청 없이 조회만 한다. 이미 발급된 송장이 있으면 같은 번호로 등록 단계만 이어간다. 응답 유실은 기존 요청 ID로 조회하며 결과 불명 상태에서는 재발급을 열지 않는다. 확정 실패 후 안전성이 확인되는 경우만 해당 단계 재시도를 제공한다. 실제 쓰기는 기존 최종 확인 절차를 유지한다. 작업 중 반복 클릭과 다른 창/앱의 동일 주문 작업을 차단하고 실행 기록을 남긴다.

검증: 중복 클릭·재시작·응답 유실·등록 완료 뒤 재조회가 새 송장을 만들지 않음, 다른 계정/사업장 작업 접근 차단. 실주문 발급을 시험으로 실행하지 않는다.

### 5. 통합 검증 및 배포

혼합 20건의 실행·대기·실패·완료, 탭 전환, 로그인 만료, 앱 재시작, 긴 문구와 테마를 격리 코드/저장소 시험 및 오른쪽 보조 모니터의 가시 Electron 시험으로 확인한다. 설치 패키지 시험 후 빌드·로컬 설치·Ed25519 업데이트 배포·공개 파일 검증까지 수행한다. 운영 세션 읽기 검증과 모의 작업 검증의 결과는 구분한다.

## 현재 진행과 다음 작업

기획 및 기존 코드 조사 완료. 이번 반복 작업은 1단계 UI 전환을 0.198.1로 검증·배포하는 범위다. 기존 Main 진행 이벤트와 무변화 안내를 사용한다. 서버 상태 조회/재시작 복원(2단계), 오류 원인과 자동 재시도 대기 구분의 확장(3단계), 안전한 이어하기 실행(4단계)은 아직 구현 완료로 보지 않는다. 5단계의 전체 기능 통합 검증과 별도로 각 반복 작업도 설치앱·배포 검증을 수행한다.

결정: 행의 선택 버튼 내부에 details/button을 중첩하지 않고, 같은 주문 행의 상품 열 아래 형제 details를 배치한다. 주문 선택/키보드 접근성을 보존한다.

결정: 현재 뱃지 상세의 동작은 '주문 상세 확인'으로 한정한다. 아직 연결되지 않은 재시작 버튼을 제공하지 않으며 실제 재시도는 4단계의 기존 요청 검증을 통과해야 한다.

추가 검증: 0.198.0의 등록 완료 색상이 기존 배송 상태 공통 CSS에 덮이는 것을 발견했다. 진행 전용 data-progress-state로 속성을 분리한 0.198.1에서 실제 계산 색상이 mint 토큰과 일치하는 시험까지 통과했다.

1단계 검증: 코드 시험 489개 통과, 설치 패키지 161개 파일 일치, 소스 및 설치본의 오른쪽 모니터 가시 Electron 시험 통과. 공개 manifest 0.198.1의 Ed25519 서명 및 설치파일 HTTP 200/크기 확인. 실주문 발급 시험은 하지 않았다. 상세 근거는 D:\GPT\Temp\inline-shipping-20261024\verification.md에 기록했다.

다음 작업은 2단계: 계정·사업장 범위의 서버 작업 상태 조회 및 뱃지 복원이다. 현재 구현은 이번 앱 실행에서 시작한 작업의 Main 이벤트에 대한 표시이며 서버 재시작 복원이나 신규 이어하기 실행 버튼을 완료한 것으로 보지 않는다.
