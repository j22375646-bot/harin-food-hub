# P4-19 사업장별 주문 조회 경로

## 구현

`GET /api/moaon/businesses/[tenantId]/orders`를 추가했다. 기존 `/api/orders/page`를 내부 읽기 함수로 호출하며 기존 앱의 호출 주소와 UI는 변경하지 않았다.

1. 요청 형식·쿠키·출처·허용 검색조건을 검사한다.
2. 실제 서버 인증과 제어 DB에서 사업장 소속을 확인한다.
3. 하린식품에 고정 연결된 OWNER만 기존 주문 원장을 조회한다. 다른 사업장 ID나 이름으로 연결 대상을 바꿀 수 없다.
4. 주문 조회 후 다시 인증·소속·역할·소속 버전을 확인한다. 조회 중 변경되면 가져온 주문을 반환하지 않는다.
5. 응답은 캐시하지 않는다. 제한 시간이 지나면 늦게 끝난 인증으로 주문 조회를 시작하지 않는다.

기존 원장에는 사업장 구분이 없으므로 VIEWER/OPERATOR에게 임의 개방하지 않았다. 다사업장 전체 원장 이전·플랫폼 연결·쓰기 권한 분리는 별도 작업이다. 이 경로는 조회 전용이며 송장 발급/출고/주문 변경을 수행하지 않는다.

## 테스트와 적용 기록

- 테스트를 먼저 작성해 새 경로 5개와 runtime guard 주입 1개의 실패를 확인한 뒤 구현했다.
- 새 요청 경로·제어 저장소·runtime 관련 38개 시험 통과. 실제 PGlite SQL 가명 소속을 조회 중 제거했을 때 주문 결과를 반환하지 않는 통합 시험 포함.
- Next.js 16.3.0 운영 빌드 통과.
- 빌드와 병렬 실행한 전체 시험에서 기존 복구 기능 15ms 타이밍 시험 1개 실패. 해당 파일 단독 재실행 38개 통과. 이후 `node --test --test-concurrency=2 test/**/*.test.js` 전체 재실행 2,598개 통과, 실패/건너뜀 0개(154.6초). 기존 타이밍 테스트 자체는 변경하지 않았다.
- 새 경로는 DB와 같은 sin1 지역 설정을 사용한다. DB 이동/새 인스턴스/유료 고정 IP를 추가하지 않는다.

### 운영 확인

- 코드 `9eb6fd4`, 배포 `dpl_HtSXq8ZP6xYTRvQXvgkEDqEHuXbf`, Production READY, 정식 도메인 alias 완료.
- 배포 주소: https://harin-cafe24-sync-jchbpn8t6-j22375646-6156s-projects.vercel.app
- 로그인된 브라우저에서 새 경로의 `ok:true`, 세 채널 저장 자료 READY, partial=false 응답을 확인했다. 최초 시험 query는 `stage=before-issue`였으며 해당 조건의 orders는 빈 배열/total=0, 별도 업무 요약 ACTIVE count=1이었다. 실제 주문 행 수신 성공으로 과장하지 않는다.
- 올바른 `stage=ACTIVE` 재조회 및 가명 타 사업장 경로는 브라우저 도구가 `net::ERR_BLOCKED_BY_CLIENT`를 반환했다. 이것을 서버의 403 응답 증거로 취급하지 않는다. 교차 접근 차단은 이번 로컬 통합 시험에서 검증됐으며 운영 차단 응답 인수는 남았다.
- 운영 DB 변경, 실제 발급/출고, 새로운 유료 자원 생성은 없다. 앱 새 설치파일은 만들지 않았다.

## 다음 순서

새 서버 경로의 실제 로그인 인수를 확인한 뒤 앱 통신 허용 목록과 주문 조회 주소를 전환한다. 서버 호출이 가능한 것과 새 EXE 설치 완료는 구분한다. 타 사업장 선택은 해당 사업장의 독립 원장/연결이 준비되기 전에는 허용하지 않는다.
