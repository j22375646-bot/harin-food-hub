# 모아온 P1-04-3 개발 보고서

## 이번 단계가 필요한 이유

비밀번호를 바꾸는 순간에 이전 비밀번호로 시작했던 로그인이 아직 처리 중일 수 있다. 단순히 기존 세션을 지우기만 하면, 늦게 끝난 로그인 요청이 새 세션을 다시 만들 수 있다.

P1-04-1은 이 문제를 막는 DB 차단 장치, P1-04-2는 복구 프로그램이었다. 이번 P1-04-3은 **기존 로그인 프로그램에 그 차단 장치를 연결하는 단계**다. 로그인 시작 전에 일회용 접수표를 받고, 저장 직전에도 그 접수표가 유효한지 확인하도록 한다.

## 범위와 운영 안전

- 릴리스 대상 1.45.0. 구현·검토·최종 검사 결과는 아래에 기록한다.
- 기존 하린식품 로그인 UI·비밀번호·쿠키 형식·업무 API는 유지한다.
- 새 방식은 서버 개발자가 명시적으로 주입하는 설정으로만 선택한다. 고객이 입력한 값·헤더·환경 변수로 켜지지 않는다.
- 새 방식을 선택한 뒤 문제가 생겨도 이전의 직접 세션 저장 방식으로 돌아가지 않는다.
- 운영 인증 설정·DB 스키마 적용·실제 비밀번호 변경·메일 발송은 하지 않는다. 다른 사업장 가입이나 EXE 설치 기능을 이번 단계의 완료로 표시하지 않는다.
- 별도 유료 테스트 브랜치·서버·서비스를 만들지 않는다. PC 내부의 합성 사용자·인증 응답·PGlite SQL 검증이며 실제 Supabase Auth/SMTP 또는 실제 다중 DB 연결 검증과 다르다.

## 확인한 로그인 연결 지점

기존 실행 경로는 `/api/dashboard/login` → `authenticateAccount` → `createDatabaseSession` → `dashboard_sessions` 저장이다. 그 외 신규 후보 SQL의 `moaon_issue_session`이 차단 장치를 거치는 저장 경로다. `createSessionToken`은 서명 문자열을 만드는 함수이며, 이것만으로 DB 세션을 생성하지 않는다.

이번에는 기존 인증·저장 함수의 서버 연결부를 준비한다. 운영 route는 기존 인수로 호출하므로 자동 전환되지 않는다. 후보 SQL을 적용하고 실제 호출부를 전환하기 전까지는 **운영의 모든 로그인에 차단 장치가 적용됐다고 주장하지 않는다.**

## 구현·검증한 핵심 상황

1. 로그인 인증보다 일회용 접수표 발급이 먼저 실행되는지.
2. 복구 이전에 시작한 지연 로그인이 복구 후 세션을 만들지 못하는지.
3. 이미 발급된 세션은 복구 시작 시 폐기되고 다른 계정의 세션은 유지되는지.
4. 복구 후 새 비밀번호 인증으로 시작한 새 로그인은 가능한지.
5. 인증 결과와 최신 프로필의 ID·이메일·활성 상태가 일치하는지.
6. 저장 거부·시간 초과·불확실한 응답에서 토큰을 돌려주거나 직접 저장으로 우회하지 않는지.
7. 직전 검토에서 남긴 자동 갱신 요청 차단 시험이 URL query를 실제로 확인하는지.

## 결과

### 검토에서 발견해 보완한 내용

- 계정 정보를 재조회한 뒤 실제 저장 직전에도 정보가 바뀔 수 있어, 인증한 프로필과 DB의 현재 프로필을 같은 저장 작업 안에서 비교하도록 후보 SQL 연결 계약을 보완했다. 불일치하면 세션 발급을 거부한다.
- 인증 서버가 오류 없이 불완전한 응답을 돌려주면 잘못된 비밀번호로 횟수를 누적하지 않고, 인증 서비스 확인 필요로 처리한다.
- 이에 따라 “후보 SQL 파일도 변경하지 않는다”는 내부 계획은 최소 비교 기능에 한해 조정했다. 운영 DB에는 적용하지 않는다. 판단이 잘못됐다면 후보 SQL과 연결부의 호환성 재작업이 필요하지만 운영 스키마는 바뀌지 않는다.
- 앱과 DB의 시계 차이에 따른 12시간 만료 상한 판정은 운영 활성화 전 확인할 별도 항목이다.

### 검사 기록

검토 보완 커밋 `b0e06bb`에서 인증·로그인 장애·세션 저장·후보 SQL·계정 복구·SDK 연결 검사 100/100 통과(실패·건너뜀 0)를 확인했다. 실제 후보 SQL에 저장 직전 이메일·사용자명·권한 변경을 주입하면 모두 세션 0건, 접수표 미소비로 거부됐다. 이전 5개 인자 호출도 호환성을 유지한다. 단, 실제 새 로그인 경로는 항상 검증한 프로필을 함께 보내며, 운영 전환 시 모든 발급 경로가 이를 지켜야 한다.

구현 커밋 `ac7dd57`. 기준 코드의 집중 검사 45개에 새 로그인 시험 16개를 더해 61개를 검사했다. 구현 담당 결과는 집중 61/61, 인접 인증·세션 차단 검사 37/37, 전체 2,153/2,153 통과다. 주 작업자도 집중 61/61을 다시 확인하고 `pnpm build` 성공 후 순서대로 `pnpm test`를 실행해 전체 2,153/2,153 통과(실패·건너뜀 0)를 확인했다. 독립 검토와 운영 배포 결과는 완료 시 확정한다.

이전 단계의 자동 갱신 차단 시험은 URL query를 검사하도록 보강했다. 차단 코드를 임시 제거하면 15개 중 1개가 실패했고, 즉시 복원한 뒤 15개가 모두 통과했다. 약화된 코드는 커밋하지 않았다.

PGlite에서는 A/B 계정의 실제 로그인 함수와 후보 SQL을 연결했다. A의 로그인을 지연시키고 그 사이 복구를 시작·완료하면, 이전 A 세션이 폐기되고 지연 로그인도 거부됐다. B 세션은 유지됐고, A가 복구 후 새 로그인을 시작하면 정상 발급됐다. 이는 실제 SQL의 결정적 순서 검증이지 운영 Supabase에서 비밀번호를 변경했다는 뜻은 아니다.

SDK의 의도적으로 만료시킨 모의 세션 시험에는 고정된 `Recovery session refresh is disabled.` 진단이 출력될 수 있다. 실제 갱신 요청은 전달하지 않으며 이 메시지에 비밀번호·토큰·이메일·공급자 원문은 포함하지 않는다.

## 이어서 할 작업

1. 운영 SQL·호출부 전환의 사전 검사와 복구 절차를 준비한다.
2. 서버 재시작·동시 요청에도 일관된 요청 제한, 복구 실패 계정의 운영자 검토와 이력을 연결한다.
3. 허용 수신자와 실제 SMTP 설정으로 메일·만료 링크·재사용 링크·로그아웃을 검증한다. 새 비용이 생기는 자원은 임의로 만들지 않는다.
4. 실제 인증 전환 후 사업장별 주문·정산·파일·캐시 격리(P2), 플랫폼 연결(P3), Windows UI·설치 프로그램 순서로 진행한다.
