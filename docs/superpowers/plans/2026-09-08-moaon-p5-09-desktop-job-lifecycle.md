# P5-09 후속: Windows 발급 작업 상태 및 재시작 복구 코어

## 완료 범위

운영 worker 배포 다음 단계로, Main 프로세스용 발급 작업 상태 머신과 사업장별 디스크 기록 모듈을 추가했다. 아직 main.cjs, IPC, UI, 실제 HTTP 통신 및 EXE 패키지에는 연결하지 않았다. 앱의 조회 전용 정책은 그대로다.

- 전송 전에 주문 식별자와 SUBMITTING 상태를 파일에 저장한다. 저장 실패 시 POST하지 않는다.
- 접수된 요청 번호로 GET 조회만 이어간다. 중복 클릭과 동시 조회를 단일 실행으로 제한한다.
- 전송 후 응답 유실·시간 초과는 UNKNOWN으로 남긴다. 자동 재발급하지 않는다.
- 프로세스 재생성 시 저장 기록을 복구한다. 요청 번호가 있으면 조회 가능하며, 번호가 없으면 대조가 필요하다.
- 주문 번호·요청 번호가 일치하고 송장 번호 형식까지 확인된 응답만 성공으로 판정한다.
- 저장 필드는 버전, 사업장, 주문 ID, 요청 ID, 상태뿐이다. 수취인·연락처·주소·원문 오류·송장 번호는 기록하지 않는다.
- 사업장 키를 해시한 파일명, 4KB 제한, 임시 파일 동기화 후 같은 디렉터리 rename을 적용했다. 손상 기록을 빈 작업으로 초기화하지 않는다.

## 검증

새 전용 테스트 17개 및 데스크톱 전체 65개 통과. 합성 API 응답과 임시 디스크 파일만 사용했다. 실제 고객 주문 발급, 새 유료 리소스 생성, 운영 데이터 복사는 없었다.

기존 웹 회귀 테스트도 `node --test --test-concurrency=4 'test/**/*.test.js'`로 2,548개 모두 통과했다. 이는 실제 외부 API 발급 성공이나 UI 통합 검증을 대신하지 않는다.

TDD에서 배열 형태 ID가 문자열로 암묵 변환되는 실패를 재현하고 타입 검사를 추가했다. 코드 검토에서 기존 파일 내용이 JSON null일 때 기록 부재로 오인하는 결함을 발견했다. 실패 테스트 2개를 확인한 후 읽기·쓰기 모두 차단하여 재검증했다.

## 제한과 다음 연결 작업

이 모듈은 실행 권한이나 완성된 발급 기능이 아니다. 호스트는 인증된 사업장 고정, 최신 주문 확인, 네이티브 확인창, 신뢰된 IPC 발신자 검증, 사업장당 단일 컨트롤러를 보장해야 한다. 현재 한 작업의 수명주기만 처리하며 다음 주문을 위한 안전한 이력 전환·대조 절차는 별도 연결 대상이다.

파일 저장은 프로세스 중단 복구를 대상으로 하며 모든 파일시스템의 정전·디스크 장애를 보증하지 않는다. CANCELLED의 현재 서버 응답에 식별자가 없으면 UNKNOWN으로 유지한다.

다음은 Main 호스트/고정 API 전송 연결 → 발급 전 확인 및 상태 UI → 로그아웃·재시작·타임아웃 통합 테스트 → 새 EXE 빌드 및 실행 검증 순서다. 실주문 발급과 프린터 출력은 별도 명시적 확인 후 검증한다.
