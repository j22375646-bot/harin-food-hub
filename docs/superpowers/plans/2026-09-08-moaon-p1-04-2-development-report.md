# 모아온 P1-04-2 개발 보고

## 사용자에게 의미하는 변화

이전 P1-04-1은 비밀번호 변경 때 기존 로그인 기록을 안전하게 폐기하는 DB 장치였다. 이번 P1-04-2는 그 장치를 인증 공급자의 이메일 확인·비밀번호 변경 API와 연결하는 서버 프로그램이다.

기존 하린식품 로그인 화면·비밀번호·업무 기능은 유지한다. 새 복구 기능은 운영 로그인에 아직 활성화하지 않는다. 이 문서의 로컬 검증을 실제 이메일 도착이나 운영 계정 복구 성공으로 해석하면 안 된다.

## 비용과 운영 자료 보호

- 이번 단계에는 유료 Supabase 브랜치, 새 VPS·클라우드 서버, 유료 메일 서비스를 생성하지 않는다.
- 테스트는 PC 내부에서 합성 계정과 인증 응답 시뮬레이션을 사용한다. 실제 Supabase SDK를 통과하는 요청 계약을 시험하지만 실제 Supabase Auth 엔진 검증과는 다르다.
- 실제 수신자에게 메일을 보내지 않고 운영 Auth·DB 설정이나 비밀번호를 수정하지 않는다.
- 기존 요금제의 일반 서비스 사용료까지 0원이라고 보장하는 의미는 아니다. 이번 개발을 위해 별도 유료 테스트 자원을 추가하지 않는다는 뜻이다.

## 구현한 흐름

1. **복구 메일 요청:** 고정된 복구 주소만 사용하고 요청 제한 검사를 먼저 거친다. 등록되지 않은 계정·중지된 계정·메일 서버의 발송 오류에는 같은 접수 응답을 돌려줘 계정 존재 여부를 노출하지 않는다. 접수 응답은 메일 도착 확인과 다르다.
2. **이메일 확인:** 확인용 링크를 인증 서버에서 검사하고, 최신 계정 상태와 허브 프로필의 ID·이메일을 대조한다. 사업장 가입이나 로그인 세션은 자동 생성하지 않는다.
3. **비밀번호 변경:** 복구용 링크 검증 → 계정 확인 → 기존 세션 차단 → 비밀번호 변경 → 인증 공급자 세션 폐기 → 최신 계정 재확인 → 잠금 해제 순서다. 새 비밀번호는 12~128자이며 기존 하린식품 비밀번호에는 이 규칙을 적용하지 않는다.
4. **실패 처리:** 처리 결과가 불명확하면 `REVIEW_REQUIRED`로 남기고 자동 재시도·잠금 해제를 하지 않는다. 시간 제한 뒤 늦게 도착한 응답으로 후속 변경이 실행되지 않게 한다.
5. **동시 계정 보호:** 복구 작업마다 인증 클라이언트를 따로 만들며, 비밀번호와 인증 토큰을 화면 응답·오류·진단에 포함하지 않는다.

공급자 로그아웃만으로 이미 발급된 access JWT가 즉시 모두 무효가 되는 것은 아니다. 허브의 DB 세션 차단 장치와 향후 업무 API의 재검증이 함께 필요하다.

## 운영 개방 전 반드시 남겨둘 조건

1. 기존 로그인 세션 생성 경로를 모두 P1-04-1 접수표 방식으로 연결하고 회귀 검증한다. 기존 직접 세션 저장과 새 복구 기능을 혼용하지 않는다.
2. 실제 메일 발송 설정·허용한 수신자·콜백 주소를 확인하고 이메일 도착, 만료·재사용 링크를 시험한다.
3. 공개 HTTP 경로의 CSRF, 링크 노출 방지, 사용자 존재 여부 숨김, 지속형 요청 제한을 검증한다. 모듈의 서버 제한 의존성만으로 운영 요청 제한이 배포됐다고 보지 않는다.
4. 비밀번호 변경 여부가 불명확해 잠긴 계정의 확인·복구 작업공간과 이력을 구현한다. 임의 자동 잠금 해제는 금지한다.
5. 사업장별 주문·정산·파일·알림 격리(P2) 완료 전 다른 사업장의 실데이터 가입·연결을 열지 않는다.

### 검토 중 찾아서 수정한 부분

- 링크 확인 직후 최신 계정 조회가 실패하면 임시 인증 세션을 정리하지 못하던 경로를 수정했다.
- 허브의 대기 시간이 끝난 뒤 인증 결과가 늦게 도착해도 임시 세션을 한 번 정리하고, 비밀번호 변경·잠금 해제를 이어서 실행하지 않게 했다.
- 실제 SDK 요청을 통과하는 비밀번호 변경·전체 로그아웃의 시간 초과 및 실패 시험을 추가했다.
- 서버 시각 확인 함수가 실패해도 내부 오류 내용이 사용자에게 노출되지 않게 했다.

위 네 항목은 독립 재검토에서 모두 해결된 것으로 판정했다. 실제 메일 도착·운영 계정 비밀번호 변경을 시험했다는 뜻은 아니다.
