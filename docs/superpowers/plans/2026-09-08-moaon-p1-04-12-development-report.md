# 모아온 P1-04-12 개발 보고서

## 목적과 현재 상태

저장된 추가 인증 결과를 복구 검토 요청에서 실제로 사용하고, 대기 중 폐기된 인증으로 작업이 계속되지 않도록 보완한다. 기존 부품을 연결하는 단계이며 새 로그인 화면이나 실제 MFA 활성화는 아니다.

시작 소스 `f164670`, 기준 전체 검사2,435/2,435 통과(60.28초). 구현 커밋 `718bd3c`의 집중 검사70/70(15.26초), 기존 통합 호환성14/14(18.64초)가 통과했다. 보완 커밋 `d21e473`에서 집중 검사169/169, 전체 검사2,448/2,448(58.97초, 실패·취소·건너뜀0)이 통과했다. Next 빌드도 통과했다. 독립 최종 검토·배포 확인은 진행 중이다.

## 구현 및 검증 범위

- 실제 저장소의 인증 필요 오류를403으로 구분한다. 오류 코드만 흉내 낸 객체나 실제 장애는 원문을 숨긴503으로 유지한다.
- 요청 제한 검사와 로그인 재확인 후 추가 인증을 다시 조회한다. 대기 중 폐기된 인증은 조회/종결 작업을 실행하지 못한다.
- 처음 인증의 만료를 늘리지 않으며 요청 안의 모든 시각 검사는 같은 단조 시각 관측기를 사용한다. 시계가 뒤로 가거나 요청이 만료·취소되면 다음 작업을 보내지 않는다.
- 세 결함을 각각 실패로 재현했다: 인증 없음이503 반환, 성공 경로의 저장소 조회가1회뿐, 부분 시계 역행에도200 반환. 수정 후 통과했다.
- 신규 통합 검사에서는 실제 handler·PGlite SQL·createStepUpStorage의 발급/조회/폐기를 사용했다. 공급자 인증 결과·로그인 신원·별도 admission/resolver 응답은 합성 자료다. 실제 공급자 로그인이나 운영 SQL 성공을 의미하지 않는다.
- 수정 범위는 내부 요청 처리1개와 관련 테스트·합성 인증 fixture다. 기존 공급자/저장소/SQL/로그인/화면/환경 설정은 바꾸지 않았다.

## 전체 검사 중 발견한 테스트 타이밍 문제

첫 전체 실행에서 기존 SDK 수직 테스트가 실패했다. 인증 시간을 시험 준비 시점에 고정한 뒤 실행이 지연되면, DB 인증 시작보다 과거가 되어 정상 보안 검사에 거부되는 것이 원인이었다. 1.1초 지연으로 동일 실패를 재현했다. 운영 인증 검사를 완화하지 않고 합성 인증 응답 시점에 테스트 JWT를 다시 서명하도록 보완했다. 독립 검토에서 지적된 잘못된 쿠키의 proof 조회0회와 정상 쿠키의2회 명시 검사도 추가했다. 수정 후 전체2,448개가 통과했다.

## 개발 중 정한 조건

1. 공개 경로와 운영 인증은 아직 비활성이다. 검증되지 않은 인증 전환을 막는 대신 새 사용자 로그인은 후속 검수를 기다린다.
2. 요청 제한 검사 후 인증이 폐기돼 거절돼도 이미 사용한 요청 횟수는 돌려주지 않는다. 중복 요청 제한을 일관되게 유지하지만 거절된 요청도 한도를 소비할 수 있다.
3. 같은 사용자·로그인의 새 유효 인증은 받아들일 수 있으나 최초 요청의 허용 시간을 늘리지 않는다. 사용자는 새 요청을 시작해야 할 수 있다.
4. 마지막 재조회와 외부 변경을 하나의 DB 거래로 묶지는 않는다. 이미 전달된 작업을 취소했다고 보장하지 않으며, 마지막 검사 이후의 동시 변경은 다음 요청부터 반영될 수 있다.

## 운영 연결 현황 재확인

2026-09-08 소스 읽기 기준이며 실계정 로그인 성공 검증이 아니다.

| 경로 | 현재 코드 | 활성화 전 남은 연결 |
|---|---|---|
| 기존 로그인 | app/api/dashboard/login/route.js → authenticateAccount → createDatabaseSession | 공개 호출은 sessionFence/requestLimit/accountLimit을 아직 주입하지 않음. IP 신뢰 경계와 모든 발급 경로 검수 필요 |
| 세션 확인 | validateSession은 서명·DB 세션·폐기·만료를 검사 | 신규 사업장용 identity verifier는 활성 프로필·공급자 이메일 확인까지 필요 |
| 기존 로그아웃 | app/api/dashboard/logout/route.js → revokeSession, 쿠키 삭제 | 저장된 추가 인증의 읽기는 폐기된 허브 세션을 거부하지만 암호문 물리 삭제 연결·실패 처리 검수가 별도 필요 |
| 계정 복구 | createAccountRecovery 서버 부품 | 공개 route 호출 없음, 실제 메일·복구·공급자 연동 검수 필요 |
| 추가 인증/복구 검토 | createStepUpStorage + createRecoveryReviewRequestHandler | 이번 로컬 통합 검사. 공개 route·실제 키·실계정 연결은 아직 없음 |

이 확인 결과를 이유로 기존 로그인이나 비밀번호를 임의로 바꾸지 않는다. 다음 단계는 실제 로그인·로그아웃 연결 조합의 격리 검증이며, 운영 활성화 조건을 충족한 뒤 제한적으로 전환한다. 사업장 데이터 격리(P2) 이전에는 타 사업장 실사용을 열지 않는다.
