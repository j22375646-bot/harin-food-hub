# 모아온 P1-03 개발 보고서

개발번호: **P1-03 — 로그인 신원·제한 DB 연결 기반**. 버전: **1.42.0**. 작성일: 2026-09-07.
상태: 내부 코드 구현·작업 단위 독립 검토·전체 테스트·운영 빌드 완료. 운영 배포 식별자와 상태는 배포 후 사용자 최종 보고에서 별도로 확인한다. 새 사업장 가입이나 EXE 완료를 뜻하지 않는다.

## 이번 개발이 하는 일

다른 사업장이 자기 계정으로 모아온을 사용하려면, 로그인한 사람이 누구인지 확인하는 부분과 사업장 회원 정보를 저장하는 부분이 안전하게 연결되어야 한다. 이번 단계는 그 연결부를 만든다. 설치형 EXE나 다른 사업장 가입 화면을 개방하는 단계는 아니다.

### 로그인·이메일 확인

기존 로그인 세션을 유지하면서 새 회원 기능에서는 현재 계정 활성 여부와 인증 서버의 이메일 확인 기록을 함께 검사한다. 화면에서 전달한 이메일 인증 표시나 사업장 권한을 믿지 않는다. 인증 서버 장애나 만료된 로그인은 통과시키지 않는다.

### 회원·초대 DB 연결

회원 관리에 필요한 권한만 가진 전용 DB 계정을 사용하도록 한다. 가입 처리 도중 오류가 나면 회원 생성·초대 사용 처리·감사 기록이 일부만 저장되지 않게 한다. 같은 초대를 동시에 누르는 상황도 별도로 시험한다.

## 실제로 확인한 환경

- 운영 DB의 메타데이터만 조회: PostgreSQL 17.6, public 테이블 129개, tenant_id 컬럼 0개, moaon_control 스키마 없음. 고객·주문·계정 행은 변경하지 않았다.
- Auth 저장소의 사용자 ID·이메일·이메일 확인 시각·차단 만료·삭제 시각·익명 여부 필드 존재와 타입도 확인했다. 사용자 행이나 실제 인증 응답을 검증한 것과는 다르다.
- 테스트 DB: 이 PC의 PostgreSQL 17.11, 127.0.0.1:55437 내부 접속, SCRAM 비밀번호 인증. 유료 서버나 Windows 서비스를 추가하지 않았다.
- 공식 EDB Windows ZIP은 341,325,378바이트. SHA256 `4B8DB0930C38F6EF845DB919551DEDDA3B6B845AEB0927B3D79A6E8E9E4537CF`. 실행 파일은 Authenticode 서명이 없으며 이 해시는 다운로드 파일 식별값이지 별도 서명 검증을 대신하지 않는다.
- 한글 경로에서 initdb의 UTF-8 오류가 재현되어 같은 실행 파일·옵션을 영문 임시 경로에서 실행했고 초기화에 성공했다. 운영 DB 오류가 아닌 로컬 검증 도구 경로 문제다.
- PostgreSQL 연결 드라이버 pg 8.23.0을 정확한 버전으로 고정했다. 설치 스크립트는 실행하지 않았다.

## 아직 열지 않는 기능

- 실제 다른 사업장 가입, 초대 이메일 발송, 사업장 전환 화면.
- 운영 DB의 신규 스키마·역할 전환. 현재 SQL은 자동 적용 migration이 아닌 검토 후보 파일이다.
- 비밀번호 재설정의 전체 흐름. 현재 코드에는 기존 세션을 폐기하는 함수가 있지만 reset 경로가 없으므로 자동으로 연결됐다고 보고하지 않는다.
- Windows EXE 설치·프린터 실출력. 후속 앱 단계에서 별도 검증한다.

전용 회원 DB 역할은 내부 회원 관리 범위의 권한이다. 주문·정산·파일 등을 사업장별로 분리하는 P2 검증을 대체하지 않는다.

## 검증 및 릴리스

- 최종 로그인 신원 집중 테스트 **48개 통과**. PostgreSQL adapter 집중 테스트 **41개 통과**.
- 최종 전체 회귀 테스트 **2,078개 통과 / 실패 0 / skip 0**, UI 규칙 검사 통과(기존 부채 518개 유지).
- Next.js 16.3.0 **운영 빌드 성공**. 기존 module-type 경고는 남아 있으며 이번 인증 작업에서 전체 모듈 체계를 바꾸지는 않았다.
- 실제 PostgreSQL 17.11 **8개 통과 / 실패 0 / skip 0**. 작업 단위 수정 후 전체 제어자가 별도로 재실행했다. 동시 연결 PID는 초대 30260/36776, 관리자 28160/29860, 수락·회수 36888/10624로 서로 달랐다.
- 전체 검사의 첫 실행에서 버전 1.42.0 변경 이력이 빠진 문서 검사가 실패했다. CHANGELOG를 보완한 뒤 위 최종 전체 검사에 통과했다.

실제 DB 시험에서는 초대 중복 수락 시 회원 1건만 생성되고, 관리자 두 명의 동시 권한 변경 후에도 관리자가 최소 1명 남으며, 감사 기록 저장 실패 시 회원·초대 변경 전체가 취소되는 것을 확인했다. 각 동시 작업은 서로 다른 DB 연결을 사용했다.

개발 전 운영 기준선은 1.41.0이며 `/login` 200, `/orders` 307 로그인 이동, 주문/운영 알림 API는 미로그인 401을 확인했다. 이는 배포 후 검증과 별도로 기록한다.

독립 검토에서 `2026-02-31`처럼 존재하지 않는 날짜를 JavaScript가 다른 날짜로 바꾸는 사례를 확인했다. 이메일 인증 시각·차단 만료·세션 만료가 같은 엄격한 달력 검증기를 사용하도록 수정했고 집중 시험 48개와 재검토를 통과했다. 실제 고객 데이터에서 발생한 사고를 확인한 것은 아니며, 신규 코드의 경계값 시험에서 찾은 결함이다.

DB 검토에서는 암묵적인 환경변수 접속 설정 사용, 검증한 TLS 객체의 사후 변경, 시험 준비 실패 시 기존 역할을 삭제할 수 있는 정리 경로를 찾았다. 명시적 설정·TLS 복사·자원 소유권 추적 및 정리 오류 보고로 수정했다. 세 항목 모두 재검토 통과했고, 기존 역할이 있는 실패 시험에서 해당 역할이 살아 있는 것도 확인했다.

## 다음 개발

1. P1-04: 이메일 발송·비밀번호 재설정·구 세션 폐기 흐름과 별도 검증 환경 연결.
2. P2: 주문·문의·상품·정산·파일·캐시·알림·수집 작업의 사업장별 격리와 기존 하린식품 자료 대조.
3. P3: 사업장별 플랫폼 직접 연결·비밀키 보관·독립 수집 작업.
4. P4/P5: PC 전용 UI와 EXE 설치·업데이트·송장 인쇄 검증. 화면 시안·모의 장비 시험과 실제 신규 사업장 개방은 구분한다.

### 다음 P1-04의 완료 기준

- 이메일 확인과 비밀번호 재설정은 실제 인증 공급자의 흐름에 연결하고, 재설정 후 이전 세션으로 새 요청이 통과하지 않게 한다.
- 만료·이미 사용한 링크, 중지된 계정, 메일 장애를 시험한다. 기존 하린식품 로그인은 별도의 회귀 시험으로 보호한다.
- 운영 자료와 분리한 검증 환경에서 제한 DB 계정과 TLS 인증서를 확인한다. 유료 환경이나 실제 이메일 발송이 필요하면 그 지점의 권한·설정을 먼저 확인한다.
- 이 항목이 끝나도 P2 사업장별 자료 분리가 검증되기 전에는 다른 사업자의 실데이터를 넣지 않는다.

## 이번 단계의 판단과 남는 비용

- 비밀번호가 바뀌었다는 증거로 단순 계정 수정 시각을 사용하지 않는다. 대신 실제 재설정·세션 폐기 연결을 다음 단계에서 구현해야 한다.
- 운영 DB 대신 PC 내부의 별도 PostgreSQL에서 동시성을 시험했다. 운영 자료 변경 위험을 피했지만, 호스팅 환경의 인증서·연결 풀·접속 권한은 아직 별도 검증이 필요하다.
