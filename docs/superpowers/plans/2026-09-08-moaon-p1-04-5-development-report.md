# 모아온 P1-04-5 개발 보고서

> **현재 상태:** `1.47.0`은 UNRELEASED 후보입니다. Task 1 요청 제한만 로컬 구현·검증을 마쳤고, Task 2 복구 검토 이력은 PENDING입니다. P1-04-5 전체 완료·운영 배포 보고서가 아닙니다.

## 무엇을 바꾸는가

이번 후보 단계는 로그인과 비밀번호 복구의 요청 제한을 DB에 안전하게 저장하고, 이후 복구 도중 문제가 생기면 확인할 이력을 남기는 서버 기반을 준비한다. 현재는 요청 제한만 구현됐으며 운영 화면을 바꾸거나 새 가입 기능을 개방하지 않았다.

### 요청 횟수 제한

기존 로그인 실패 기록은 DB를 읽고 횟수를 계산한 뒤 다시 쓰므로 동시 요청에서 누락될 수 있는 구조다. 새 요청 제한은 DB 잠금 안에서 한 번에 판단한다. 서버 프로그램을 새로 띄워도 같은 DB에 저장된 횟수를 계속 사용한다. 기존 비밀번호 실패 차단 정책은 없애지 않는다.

| 대상별 요청 종류 | 새 고정 창 한도 |
|---|---|
| 로그인 | 15분 10회 |
| 복구 메일 | 1시간 3회 |
| 비밀번호 복구 완료 요청 | 15분 5회 |
| 이메일 확인 | 15분 5회 |

이 값은 아직 운영에 켜지 않은 새 경로의 정책이다. 성공·실패와 관계없이 외부 인증 호출 전 소비한다. 계정/이메일/토큰 원문은 제한 테이블에 넣지 않고 서버 비밀키로 계산한 식별값을 쓴다. 저장소가 고장 났다고 제한을 건너뛰지는 않는다.

### 복구 검토 이력 — Task 2 PENDING

다음 Task 2에서 비밀번호 변경 전에 PENDING 이력을 먼저 기록하는 방식을 구현할 예정이다. 처리 중 서버가 중단돼도 시작 흔적이 남고, 결과가 불명확하면 REVIEW_REQUIRED로 남겨야 한다. 기록 자체가 계정 잠금을 풀거나 비밀번호 변경을 다시 실행해서는 안 되며, 작업 완료는 실제 DB 복구 완료 근거가 있을 때만 기록한다.

계획된 검토 목록은 서버 전용이다. 다른 사업장 관리자에게 전체 계정 정보를 노출하는 화면/API는 만들지 않는다. UUID·고정 단계·상태·DB 시각만 저장하고 비밀번호·토큰·메일·공급자 오류 원문은 기록하지 않는다.

## 검증과 운영 반영 범위

- 시작 기준71ee7c0, 전체2,167/2,167 통과, 실패·취소·건너뜀0.
- 기존 PC의 PostgreSQL17.11을127.0.0.1:55437에서 재사용한다. 운영 DB 복사나 외부 유료 테스트 자원 생성 없이 가상 계정만 쓴다.
- 요청 제한: 먼저 실패 재현41개 중 예상 실패8개를 확인한 뒤 구현했다. 집중49/49, 실제 PostgreSQL 다중 연결2/2, 전체2,182/2,182를 통과했다. 담당 구현과 별도로 PostgreSQL 검사를 다시 실행해2/2 통과를 확인했다.
- 동시 요청은20건을 보내 한도가10건인 경우 정확히10건만 허용되는지 검사했다. 별도 DB 연결의 실제 잠금 대기, 롤백 후 처리, 저장소를 닫고 다시 열어도 제한이 유지되는지 확인했다.
- 최초 동시성 검사에서는 테스트 연결을 너무 많이 열어1건이 실패했다. 테스트 연결 풀을4개로 제한하되20건의 요청은 유지한 후 통과했다. 운영 DB에 발생한 오류가 아니다.
- Task 2 복구 검토 이력과 최종 전체 검증 결과는 완료 후 추가 기록한다. 운영 배포는 별도 승인·검증 게이트이며 현재 수행하지 않았다.
- 현재 운영 로그인·비밀번호·UI·업무 API는 유지한다. 새 SQL은 미적용 후보 파일이며 새 서버 의존성을 운영에 연결하지 않는다.

## 남아 있는 조건

대상별 제한은 IP/전체 서비스 요청량 제한과 다르다. 아이디·이메일 별칭 통합, 만료 제한 기록 정리/보관 정책, 지원 관리자 검토 화면 및 안전한 수동 해결 절차, 실제 Auth/SMTP/HTTP 전환 시험은 개방 전에 추가해야 한다. 이번 구현만으로 분산 공격 방어 또는 실제 다사업장 가입이 완료됐다는 뜻이 아니다.

이후 사업장별 업무 데이터 격리(P2), 플랫폼 연결(P3), 앱 UI(P4), Windows EXE/프린터(P5)를 이어간다.
