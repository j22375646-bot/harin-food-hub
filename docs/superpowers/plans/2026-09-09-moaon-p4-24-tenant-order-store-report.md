# P4-24 — 사업장별 주문 요약 저장소

작성일: 2026-09-09

## 무엇을 개발했나요?

다른 사업장도 모아온을 쓰려면 같은 주문번호가 있어도 다른 회사 자료를 가져오거나 덮어쓰면 안 된다. 이를 위해 기존 하린식품 주문 테이블과 별개의 **주문 요약 저장소 후보**를 만들었다. 아직 실제 앱에 개방한 기능은 아니다.

식별 기준은 `사업장 + 플랫폼 연결 + 플랫폼 주문번호`다. A와 B에 같은 주문번호가 있거나, 한 사업장이 여러 플랫폼에서 같은 번호를 받아도 각각 별도 행이 된다. 연결 정보와 주문 사이에도 사업장까지 포함한 외래키를 둔다.

### 추가 파일

- `lib/tenancy/sql/order-ledger.sql`: 공개 권한 없는 별도 연결 메타데이터/주문 요약 테이블, 복합키/FK, 강제 RLS 정책. 자동 적용 migration이 아니며 운영에 실행하지 않았다.
- `lib/tenancy/order-store.js`: `save(context,input)`, `get(context,key)`, `list(context,{limit})`. 기존 서버가 발급한 context만 허용한다.
- `test/tenant-order-store.test.js`: 실제 로컬 PGlite SQL과 제한 역할을 사용한 가명 A/B 검증. 운영 주문을 복사하지 않는다.

## 동작과 제한

- 서버가 발급한 사업장 context로만 처리한다. 요청 본문 tenantId나 임의 context 복제본은 거부한다.
- 저장은 OWNER/OPERATOR, 조회는 기존 workspace.read 역할 정책을 따른다. 이 정책을 운영 하린식품 API에 적용한 것은 아니며 운영 API의 OWNER 제한은 유지한다.
- 활성 연결에만 저장·조회한다. 해제 완료된 연결의 기존 주문은 노출하지 않고 삭제하지도 않는다.
- 같은 갱신시각의 재수집은 변경하지 않는다. 더 오래된 자료는 최신 상태를 덮어쓰지 않는다. 공급자별 시각/버전 의미와 같은 시각의 상충 자료 처리는 연결 adapter 단계에서 확정해야 한다.
- 금액은 정수 또는 null이다. 미확인 금액을 0으로 보정하지 않는다. 현재 요약 모델은 상품명 하나·상태·금액·원천 갱신시각이며, 상품별 옵션/수량·배송지·환불·금액 단위 등 전체 주문 모델은 아직 없다.
- API 키나 임의 원본 payload는 입력받지 않는다. connections 테이블은 연결 ID/사업장/플랫폼/상태만 보관하며, OAuth·암호화된 비밀키 보관 기능이 아니다.
- 목록은 기본 50개, 최대 100개로 제한한다. 안정된 페이지 cursor/snapshot API는 아직 없다.
- SQL은 값 매개변수를 사용하고 오류 원문을 외부 결과에 노출하지 않는다.
- tenant 설정은 transaction-local이다. 로컬 SQL에서 성공/롤백 후 다음 요청에 설정이 남지 않는 것을 확인했다.

## 시험 결과

테스트 우선 개발로 미구현 모듈에서 첫 실패를 확인한 뒤 저장소를 구현했다. 첫 제한 역할 시험에서 행 잠금용 연결 UPDATE 권한 부족이 드러났고, 권한을 확대하는 대신 잠금을 제외했다. **따라서 연결 해제와 주문 저장의 동시 경합 안전성을 이번 결과로 주장하지 않는다.** 운영 개방 전 별도 제어가 필요하다.

신규 8개 시험:

1. A/B의 같은 주문번호 독립 저장·상세·목록.
2. 타 사업장 연결 ID 저장 거부·상세 미노출.
3. 같은 사업장의 Cafe24/쿠팡 연결별 번호 충돌 방지.
4. 중복·역순 수집과 미확인 금액 null 보존.
5. 위조 context·조회 역할 저장·본문 tenant/비밀값/잘못된 값 거부.
6. SQL에 tenant 조건이 빠져도 RLS 격리, 교차 쓰기 거부, 성공/실패 후 tenant 설정 해제.
7. 연결 해제 후 저장/조회 차단과 다른 연결 유지.
8. 조회량 제한, SQL 형태 주문번호의 문자 처리, DB 오류 원문 차단.

실행 명령:

```text
node --test --test-concurrency=2 test/tenant-order-store.test.js test/tenant-control-store.test.js test/tenant-context.test.js test/tenant-permissions.test.js test/workspace-orders-request.test.js test/business-list-service.test.js test/business-list-request.test.js
```

결과: **66개 통과 / 실패 0 / 건너뜀 0**, 약 5.44초. 로컬 PGlite 단일 연결 검증이며 실제 PostgreSQL 다중 연결 경합이나 운영 pool 검증을 대신하지 않는다. 전체 Hub 테스트/Next 빌드는 이번 신규 모듈이 운영에 연결되지 않아 수행하지 않았다.

## 운영 영향

운영 DB·권한·환경변수·API·worker·웹 배포·Windows 설치파일은 변경하지 않았다. 기존 앱 0.15.4를 유지한다. 기존 주문 원장 이전, 사업장 추가, 실계정 플랫폼 연결, 송장 발급·출력은 하지 않았다. 신규 유료 리소스와 테스트 DB 브랜치는 만들지 않았다.

## 다음 개발과 개방 조건

1. 새 업무 저장소의 전용 제한 PostgreSQL transport와 연결 해제/권한 회수 경합 제어를 구현·검증한다. 제어 DB 계정 권한을 무조건 확장하지 않는다.
2. 사업장별 플랫폼 연결 조회와 암호화 자격 증명 저장 계약을 연결한다. 임의 tenant나 임의 서버 주소를 받지 않는다.
3. 공급자 원천 시각/버전, 주문 항목·개인정보·페이지 스냅샷을 정의하고 Cafe24부터 새 저장소까지 가명 통합한다.
4. A/B 동시 요청·해제·실패 후 풀 재사용·권한 회수·늦은 응답을 검증한 후 운영 준비와 앱 전환을 단계적으로 개방한다.

모든 조건 전에는 하린식품 전용 경로를 유지하며, 다른 사업장에 기존 하린식품 자료를 대신 보여주지 않는다.
