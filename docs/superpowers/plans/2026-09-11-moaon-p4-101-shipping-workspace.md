# P4-101 — 주문 작업실 출고 결과 연결과 레이아웃 수정

## 사용자 지적과 원인

- 주문 페이지와 목록이 각각 남은 높이를 채우고, 목록/작업실/상위 페이지가 중복 스크롤했다. 결과 영역에도 최소 90px이 남았다. 데이터가 적어도 흰 카드가 늘어나고 헤더 아래 첫 행이 잘렸다.
- 자동 출고 IPC는 최종 응답만 반환했다. Main의 준비/발급/등록 단계가 화면으로 전달되지 않았다.
- 확인된 등록 결과에서 송장번호를 반환하지 않았고, renderer는 버튼만 비활성화했다. 목록 재조회와 배송대기중 전환, 행의 송장 뱃지가 빠졌다.

## 웹허브 코드 대조

검토한 중심 경로: `app/orders/page.js`, `app/_phase28/pages/orders-page.js`, `app/unified-orders-center.js`의 ShippingWorkbench, `lib/shipping/workbench.js`, `lib/shipping/fulfillment-status.js`, `lib/ui/phase28-adapters/orders.js`와 데스크톱의 발급/등록/추적 연결.

| 웹허브 기능 | 모아온 적용·연결 |
| --- | --- |
| 상품 준비 → 우체국 발급 → 플랫폼 등록 → 배송조회 | 기존 Main 검증·journal 흐름 유지. 이번에 실제 실행 단계 IPC와 원형 진행 표시 연결 |

| 실패 등록만 재시도·이력 복구 | 기존 journal/번호 재사용 경로 유지. 결과 불명 자동 재발급 없음 |
| 묶음배송 후보·수령지 비교 | 웹허브에 존재. 앱의 자동 합배송 기능으로 간주하지 않음; 별도 후보 조회/비교 설계 필요 |
| 사은품·지연 필터·채널 분리 | 기존 앱 필터·행/상세 정보 유지 |

웹허브 최초 `/orders` 접근은 로그인으로 이동했으나, 이후 인증된 세션이 확인되어 실제 주문·배송 화면과 출고 작업 탭을 읽기 전용으로 대조했다. 배송대기중에 사용자 쿠팡 쌀조청 주문 1건, 플랫폼 등록 송장번호와 우체국 접수 확인 전 상태가 표시됐다. 화면의 30초 서버 확인/배송조회 오류 2건 안내도 확인했다. 조회 과정에서 발급·등록·배송조회 실행 버튼은 누르지 않았다.

## 구현

- 페이지 하나가 세로 스크롤을 담당하도록 정리. 행/푸터는 내용 높이로 배치, 빈 결과 영역 숨김, 페이지 이동 버튼 44px 및 줄바꿈/좌우 여백 보장.
- 닫힌 상세 패널의 이동 transform이 보이지 않는 가로 overflow를 만들던 문제도 회귀 시험에서 찾아 display:none으로 제거.
- Windows MessageBox 대신 앱 dialog. Main이 만든 일회성 토큰, 지정된 Main renderer, 120초 만료, 창 닫기/탐색 취소, 이중 승인 차단. 승인 후 기존 주문 재검증은 유지.
- 취소 기본 포커스·Esc 취소·문자열 textContent·긴 내용 내부 스크롤·공통 색/44px 버튼 적용. 일정 등록 등 기존 확인 콜백도 동일한 앱 확인창 사용.
- 자동 출고에서 CHECK/PREPARE/ISSUE/REGISTER/TRACKING 진행과 서버 대기 표시. 이벤트에는 주문 식별자·단계·상태·검증된 송장번호만 전달. 완료 시 구독 해제.
- 등록 성공은 저장된 REGISTER 주문과 송장번호 일치 확인 후 표시. 배송조회 요청 접수는 배송완료로 표시하지 않음.
- 번호는 목록/최종 결과에 표시. 이미 발급되어 등록 대기인 번호도 재사용하도록 결과에 유지.
