# P4-18 서버 로그인과 사업장 권한 context 연결

## 구현한 내용

기존의 인증된 소속 조회와 권한 context 발급을 제어 저장소의 `resolveContext`로 연결했다. 요청에서 전달한 사용자/역할은 사용하지 않고 서버 세션 검증 결과와 DB의 활성 소속만 사용한다. 기존 `findMembership`과 SQL 조회 경로를 공유해 조건이 서로 달라지지 않게 했다.

쉽게 말하면 로그인 자체가 모든 사업장을 볼 수 있는 권한은 아니다. 사용자가 A에서는 소유자이고 B에서는 조회 전용이면 B에서 주문 변경 권한이 생기지 않는다. 소속 제거 또는 사업장 정지는 다음 호출에서 다시 확인한다.

발급 context는 서버의 현재 요청에서만 사용한다. 직렬화한 객체나 복제본은 기존 권한 판정기가 거부한다. 이미 발급한 context를 장기 저장하거나 작업 큐에 넣어 재사용해서는 안 된다. 실제 쓰기는 실행 시점의 별도 재검증이 필요하다.

## 검증

- 먼저 새로운 경로가 없어서 추가 테스트 3개가 실패하는 것을 확인했다.
- 구현 후 제어 저장소·context·권한·사업장 목록 request/service/runtime 시험 58개 통과, 실패/건너뜀 0개.
- 실제 PGlite SQL을 사용하는 가명 사업장 두 개로 역할 분리, 소속 제거, 사업장 정지, 무소속 사용자, 만료 인증, 잘못된 ID를 확인했다.
- git diff --check 통과. LF/CRLF 안내만 발생했다.

명령: `node --test test/tenant-control-store.test.js test/tenant-context.test.js test/tenant-permissions.test.js test/business-list-service.test.js test/business-list-runtime.test.js test/business-list-request.test.js`

## 적용 범위

서버 라이브러리와 테스트를 수정했다. 운영 주문 API가 새 메서드를 호출하도록 연결한 단계는 아니다. 기존 앱 0.15.2와 하린식품 로그인/업무 동작은 변경하지 않았다. 새로운 EXE 생성, 운영 배포, 실제 DB 변경, 운영 데이터 복제, 유료 자원 생성은 하지 않았다. 58개 테스트는 전체 허브 기능 시험이나 운영 PostgreSQL 동시성 시험을 뜻하지 않는다.

## 다음 단계

고정된 사업장과 연결된 읽기 전용 업무 진입점을 만들고 이 메서드를 호출하도록 연결한다. URL/선택값만 바꿔 기존 하린식품 원장에 접근하는 경로를 허용하지 않는다. 권한 판정 후 자료 조회 중 권한이 바뀐 경우까지 결과 반환을 검증한다. 이후 앱 사업장 선택 UI와 연결한다. 현재는 다사업장 개방 전 서버 기반 구현 상태다.
