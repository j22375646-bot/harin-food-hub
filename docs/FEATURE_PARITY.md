# 하린식품 광고·매출 진단 허브 Feature Parity 기준서

- 작성일: 2026-08-10
- 비교 대상: 기존 Genspark 멀티채널 허브 vs 현재 Next.js + Supabase + Vercel 운영 시스템
- 목적: 기존 기능을 보존하면서, 정적 대시보드를 자동 수집·검증·분석·액션·보고 시스템으로 고도화하기 위한 단일 기준서

## 1. 판정 원칙

이 문서에서 기능 보유 여부는 화면 존재 여부가 아니라 **실제 운영 수준**으로 판정한다.

- **완료**: 운영 서버와 DB에서 실제 데이터로 동작하고 검증됨
- **부분**: 일부 플랫폼·지표·화면만 동작하거나 수동 보완이 필요함
- **미구현**: 화면 안내 또는 자리만 있고 서버 기능이 없음
- **Genspark 전용**: 기존 HTML에는 있으나 정적 데이터, 브라우저 메모리 또는 수동 파일 기반임
- **보존**: 현재 정상 동작하므로 삭제·교체하지 않고 확장해야 함

> 중요: Genspark의 넓은 UI 기능과 현재 시스템의 서버 자동화는 성격이 다르다. Genspark에 버튼이나 계산 화면이 있다고 해서 서버 자동화가 구현된 것으로 간주하지 않는다.

## 2. 변경 금지 및 보존 대상

다음 기능과 구조는 정상 작동 중이므로 삭제하거나 전면 교체하지 않는다.

- Cafe24 OAuth, 토큰 자동 갱신, Admin API, Analytics API
- Cafe24 상품·주문·주문상품·트래픽·유입경로·원본 응답 저장
- 네이버 검색광고 API 인증, 캠페인·광고그룹·키워드·통계 수집
- Supabase service-role 서버 전용 사용 및 브라우저 비노출
- `sync_logs`의 RUNNING/SUCCESS/PARTIAL/FAILED 기록
- `raw_api_responses` 원본 응답 보존
- Vercel Cron의 일일 수집 및 주간 보고서 작업
- 상세 보고서 서버 계산, 인사이트 자동 반영, 실행계획 중복 방지
- Master Product 및 Channel Product 기본 구조
- 대시보드 로그인 보호와 API 인증

모든 신규 기능은 기존 테이블과 API를 유지한 채 **추가 테이블, 추가 컬럼, 공용 서비스 모듈, 신규 화면**으로 확장한다.

## 5. 자동 기능과 동일 수동 기능 대조

자동화는 UI 토글이 아니라 서버 작업이어야 하며, 동일한 서비스 함수를 수동 API도 호출해야 한다.

| 자동 기능 | 실제 서버 자동화 | 동일 수동 기능 | 판정 |
|---|---|---|---|
| Cafe24 수집 | 매일 05:30 KST Cron | `지금 동기화` / Cafe24 수집 버튼 | 완료 |
| 네이버 수집 | 매일 05:30 KST Cron | 네이버 동기화 버튼 | 완료 |
| 쿠팡 수집 | 직접 API 코드는 있으나 Cafe24 연동업체 유지로 운영 실행 보류 | WING CSV/XLSX 수동 가져오기 → DB/로그/수시보고서 자동 생성 | 보완경로 완료 |
| 전체 플랫폼 수집 | Cron 안에서 Cafe24+네이버 병렬 실행 | 전체 동기화 단일 버튼 없음 | 부분 |
| 일일 상세보고서 | 일일 수집 뒤 최근 7일 ADHOC 생성 | 날짜 지정 수시보고서로 우회 가능 | 전용 버튼 필요 |
| 일일 통합 수집 | 매일 05:30 KST · Cafe24·네이버는 Vercel, 쿠팡은 집 PC 고정 IP | 쿠팡 수동 버튼은 Realtime 이벤트로 즉시 실행 | 완료 |
| 주간 보고서 | 월요일 06:00 KST Cron | 주간 보고서 생성 폼 | 완료 |
| 월간 보고서 | 없음 | 월간 보고서 생성 폼 | 자동화 필요 |
| 키워드 실행계획 | 보고서 생성 시 무전환 TOP 자동 등록 | 감액/중지/관찰/전체 감액검토 | 완료 |
| QA 재검증 | 없음 | 없음 | 미구현 |
| 액션 효과평가 | 없음 | 없음 | 미구현 |

## 6. 데이터 QA 표준

QA는 숫자 `0`을 오류와 혼동하지 않도록 다음 상태를 강제한다.

| 코드 | 의미 | 저장 원칙 | 후속 처리 |
|---|---|---|---|
| `OK` | 정상 수집·검증 | 계산에 사용 | 없음 |
| `REAL_ZERO` | API가 실제 0을 반환 | 0으로 계산 | 이상징후 규칙만 적용 |
| `NOT_COLLECTED` | 요청하지 않았거나 연결 안 됨 | null 유지 | 수집 필요 알림 |
| `NO_DATA` | 요청 성공, 해당 기간 데이터 없음 | null/빈 배열 | 기간·계정 확인 |
| `API_ERROR` | API 실패 | 0으로 바꾸지 않음 | 재시도 후 알림 |
| `PARSE_ERROR` | 응답은 있으나 해석 실패 | raw 보존, 계산 제외 | 파서 수정/수동 업로드 |
| `PERIOD_MISMATCH` | 데이터 기간 불일치 | 혼합 계산 금지 | 동일기간 재수집 |
| `DUPLICATE` | 중복 후보 | 원본 보존, 정규 테이블 반영 차단 | 키 기준 검토 |
| `STALE` | 최신 성공 시간이 허용범위 초과 | 계산에 경고 배지 | 즉시 재수집 |

필수 QA 결과 필드:

- platform, dataset, period_start, period_end
- status_code, severity, checked_at
- rows_received, rows_valid, rows_rejected, duplicate_count
- source_request_id/raw_response_id
- expected_period, actual_period
- message, remediation, retryable

## 10. 완료 정의

기능은 다음 조건을 모두 만족해야 완료로 체크한다.

1. 서버 계산 또는 서버 수집 코드가 존재한다.
2. 자동 작업은 실제 스케줄러에서 실행된다.
3. 같은 기능을 수동으로 실행할 수 있다.
4. 실행 시작·성공·부분성공·실패가 DB에 기록된다.
5. 실제 0과 오류/미수집이 구분된다.
6. 중복 실행이 데이터 중복을 만들지 않는다.
7. 운영 UI에서 상태와 결과를 확인할 수 있다.
8. 실패와 경계값 테스트가 있다.
9. 기존 정상 기능이 회귀하지 않는다.
